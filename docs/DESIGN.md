### 데이터베이스 선택: PostgreSQL
- Supabase 프로젝트는 모두 완전한 Postgres 데이터베이스이고, Auth가 이 데이터베이스 위에 만들어져 있다. ([Supabase Database 문서](https://supabase.com/docs/guides/database/overview))
  → MySQL·MongoDB를 쓰면 Supabase 밖에 DB를 따로 두어야 하고, Supabase Auth 사용자와 DB가 분리된다.
- `AGENTS.md` 4.3은 사용자 데이터 테이블에 RLS를 요구한다. Supabase는 Postgres의 RLS로 데이터 접근을 제한한다. ([Supabase Database 문서](https://supabase.com/docs/guides/database/overview))
- 이용 기록(F-09)은 사용자 → 진단 → 문제 → 답안 → 채점처럼 서로 연결된 데이터다. Supabase Postgres는 외래 키를 지원한다. ([Supabase for Postgres Developers](https://supabase.com/solutions/postgres-developers))
- AI가 만든 문제를 당시 내용 그대로 저장(F-09)하는 데 JSONB를 쓸 수 있다. ([Supabase for Postgres Developers](https://supabase.com/solutions/postgres-developers))
  → 관계형 데이터와 문서형 데이터를 한 DB에서 다룰 수 있으므로 MongoDB를 추가할 이유가 없다.
- GraphQL은 데이터베이스가 아니라 API 질의 방식이다. API는 FastAPI가 맡고, `docs/features.md`에 GraphQL이 필요한 요구사항이 없으므로 쓰지 않는다.

### Supabase 셀프 호스팅 이전 가능성
- 클라우드 프로젝트를 셀프 호스팅으로 옮기는 공식 절차가 있다. ([Restore a Platform Project to Self-Hosted](https://supabase.com/docs/guides/self-hosting/restore-from-platform))
  - DB는 Supabase CLI로 역할·스키마·데이터를 내보내고 `psql`로 복원한다.
  - 클라우드와 셀프 호스팅의 Postgres 버전이 다를 수 있다 (예: 클라우드 17, 셀프 호스팅 기본 이미지 15).
  - JWT 비밀값·API 키, OAuth 설정, SMTP, DNS, 파일 저장소는 따로 옮기거나 다시 설정해야 한다.

## 수식 렌더링: KaTeX

### 근거: 비교 시험 (2026-11-09)
- 시험: 중학교 수식 27개를 KaTeX 0.16.47과 MathJax 4.1.3으로 렌더링. 360px·1280px, Chromium 158, 데스크톱 측정.
- 시험 코드·결과: `experiments/math-render-test/` (`results/summary.md`, `results/results.json`, 스크린샷). 로컬에만 있고 git에는 올리지 않는다 (사용자 결정, 2026-11-10). 결정에 필요한 측정값은 아래 요약에 옮겨 두었다.
- 결과 요약
  - 렌더 시간(27개, 중앙값): KaTeX 약 83ms, MathJax(줄바꿈 설정) 1.7~2.6초
  - 서버 렌더(Node): 둘 다 성공. KaTeX 18ms, MathJax 815ms
  - 360px 가로 넘침: 두 라이브러리 모두 기본 설정에서는 넘치고(KaTeX 279px), 줄바꿈 설정을 하면 0px
  - 기하 기호(≡, ∽, ∠, ⊥, ∥, `\overset{\frown}{AB}`)는 둘 다 정상
- 결정: 사용자 결정 (2026-11-09). 에이전트 추천 근거는 렌더 속도 차이(20~30배)였다. 줄바꿈 품질과 한글 글꼴은 시험에서 MathJax가 더 나았다.

### 사용 규칙
- 별도 줄 수식에는 KaTeX 공식 문서(https://katex.org/docs/issues)의 줄바꿈 CSS `.katex-display > .katex { white-space: normal }`를 적용한다. (시험에서 360px 가로 넘침 0px 확인)
  - 이 CSS는 괄호 안에서도 줄을 끊을 수 있다 (시험 S27). 넘침을 막는 안전장치로만 본다.
- 쓰지 않는 표기 (시험에서 KaTeX 미지원 확인): `\overparen`. 호는 `\overset{\frown}{AB}`로 쓴다.
- 시험하지 않은 것 (적용 전 확인 필요)
  - 한글 `\text{}` 글꼴을 본문과 맞추는 KaTeX 공식 CSS(`.hangul_fallback`, https://katex.org/docs/supported.html)
  - 긴 수식을 AI가 `\\`로 직접 줄바꿈하게 하는 방식

### 로그인 흐름 E2E (사용자 결정, 2026-11-10)
- 이유: 로그인이 필요한 화면은 가짜 env로 시험할 수 없다. 로컬 Supabase 대신 개발·테스트 프로젝트에 시험 계정 A·B(이메일 + 비밀번호, 사용자가 대시보드에서 만듦)를 두고 시험한다. 계정은 지우지 않는다. 카카오 로그인은 자동 테스트로 통과시킬 수 없어 제외한다.
- 시험 계정 환경 변수: `frontend/.env.e2e` (git 제외)의 `E2E_USER_A_EMAIL`, `E2E_USER_A_PASSWORD`, `E2E_USER_B_EMAIL`, `E2E_USER_B_PASSWORD`. Next.js는 이 파일을 앱에 읽어 들이지 않는다 ([Next.js Environment Variables](https://nextjs.org/docs/app/guides/environment-variables)).
- 명령: `pnpm test:e2e:dev` (프론트엔드). 5.2 검사 루프에는 넣지 않는다. 화면을 바꾼 단계를 마칠 때와 계획 종료 때 실행한다.
- 파일
  - 설정: `frontend/playwright.dev.config.ts`
  - 테스트: `frontend/e2e-dev/`. 기존 `pnpm test:e2e`(`testDir: ./e2e`)는 이 폴더를 읽지 않는다
- 서버: Playwright `webServer` 두 개를 띄운다. 테스트가 끝나면 Playwright가 둘 다 종료한다 (`AGENTS.md` 3.9)
  - 백엔드: `uv run uvicorn` 8000. `backend/.env`를 프로그램이 읽는다
  - 프론트: `pnpm build && pnpm start` 3000. `frontend/.env.local`을 Next.js가 읽는다
  - 이미 떠 있는 서버는 다시 쓰지 않는다. 포트를 쓰는 중이면 실패하므로 사용자 개발 서버를 끄고 실행한다
  - 브라우저 주소는 `http://localhost:3000`이다. 백엔드 CORS가 `FRONTEND_ORIGIN`만 허용하기 때문이다 (`docs/DESIGN.md` "인증 (F-01)")
- 시험 계정: 설정 파일이 `process.loadEnvFile('.env.e2e')`로 읽는다 (Node.js 내장, [Node.js process.loadEnvFile](https://nodejs.org/api/process.html#processloadenvfilepath)). 값이 없으면 바로 실패한다.
- 백엔드 webServer는 `AI_MODE=fake`로 띄운다. 실제 AI를 부르지 않는다 (`AGENTS.md` 5.4).
- 시험 내용
  1. 로그인 (`profiles`가 없으면 가입 완료 단계를 거친다)
  2. 단원 선택 → 시작 → 풀이 → 다른 화면에 갔다가 돌아와 답 확인 → 제출
  3. 같은 단원을 다시 시작하면 직전 진단과 다른 문제가 나온다
  4. 1280px·360px 가로 넘침 없음
  5. 1단계 → (통과 항목이 있으면) 2단계 → 리포트·문제별 결과, 다시 열어도 같은 리포트 (AI 재호출 없음)
  6. 교차 접근 (`gradings`·`reports` 포함): 계정 B의 진단을 계정 A가 백엔드 API로 열거나 답을 쓰면 404. Supabase에 직접 요청해도 읽으면 0행, 쓰면 거부
- 삭제는 시도하지 않는다 (2026-11-10). 테스트가 원격 데이터를 지울 수 있는 경로를 만들지 않기 위해서다. 아무 역할에도 삭제 권한이 없다는 것은 원격 권한 조회(`has_table_privilege`)로 확인했다.
- `frontend/vitest.config.mts`는 `e2e/**`와 같은 이유로 `e2e-dev/**`를 제외한다 (Playwright 파일).
- 시험 기록 정리: **지우지 않는다.**
  - 테스트는 이전 기록과 상관없이 통과하게 쓴다. 진행 중 진단은 "새로 시작"으로 중단시키고 시작한다. 변형이 3개이므로 "다시 시작하면 다른 문제"는 이전 기록이 쌓여도 성립한다.
  - 학생 역할에는 삭제 권한이 없고, 삭제 도구를 따로 만들면 원격 삭제 경로가 하나 늘어난다.
  - 기록이 너무 많아지면 사용자 확인을 받고 지운다 (`AGENTS.md` 3.2).
- 원격 쓰기 범위: 이 명령은 개발 프로젝트에 시험 계정 A·B의 진단·답안만 만든다. 사용자 결정(2026-11-10)에 따라 이 명령 실행은 매번 따로 묻지 않는다. 마이그레이션·설정 변경·삭제는 지금처럼 매번 확인한다.

### 개념 데이터 (F-03)

성취기준마다 아래 정보를 둔다.

승인된 개념 문서는 `uv run python -m app.bank convert-concepts <코드>...`로 JSON에 옮긴다. `--check`는 파일을 쓰지 않고 차이를 확인한다. (2026-11-12, 사용자 결정 "md2json.py도 저장소에 추가")
- 표 칸 안의 `|`는 문서에서 `\|`로 쓴다. 평가 항목 근거 끝의 `[그림: 본문|보기, 종류,...]`는 `figure`·`figure_kinds`로 바뀐다.
- `variants`와 용어 목록(`terms`)은 기존 JSON 값을 유지한다. 새 성취기준의 용어는 "용어" 절에서 읽으므로 적재 전에 결과를 확인한다.
- 승인 날짜는 "상태" 줄과 "사용자 승인"이 적힌 "변경" 줄 가운데 가장 늦은 날이다.
- 뒤 단원 용어는 경고로만 출력한다 (범위 문장이 제외할 용어를 일부러 적기 때문). 문제 본문의 금지 용어는 생성 코드 검사가 막는다.

| 항목 | 내용 |
|---|---|
| 성취기준 | 코드와 원문 문장 |
| 개념 | ID(`<성취기준 코드>-C<번호>`, 예: `9수02-03-C1`), 이름 |
| 평가 항목 | 개념별 (이해 수준, 근거). 근거는 "성취기준 문장의 어느 표현"인지, "에이전트 추가(이유)"인지 구분해 적는다 |
| 대표 오개념 | ID, 관련 개념, 내용, 출처 |
| 용어 | 영역의 "용어와 기호" 목록에서 가져온다 |

- 개념 단위: 개념을 크게 묶지 않는다. 문제 수가 늘어도 지금처럼 잘게 나눈다. (사용자 결정, 2026-11-09. 이유: 크게 묶으면 개념 이해 여부를 가려내는 의미가 줄어든다)
- 용어 (사용자 결정, 2026-11-09)
  - 정식 학습 용어(원문 "용어와 기호로 ~를 다룬다"): 문제·해설에 쓰고, 그 용어의 뜻을 묻는 문제도 낼 수 있다.
  - 수업용 용어(원문 "교수·학습 상황에서 사용할 수 있다", 예: 좌변, 우변, 양변): 문제·해설 문장에 자유롭게 쓴다. 그 용어 자체를 묻는 문제는 내지 않는다.
  - 초등학교와 중학교 교육과정의 "용어와 기호" 목록 어디에도 없는 수학 용어는 쓰지 않는다 (`AGENTS.md` 4.4). 이 목록들을 F-05 문제 검증에 쓴다.
  - 중학교 목록은 1~3학년이 한 묶음이라, 아직 배우지 않은 학년의 용어를 걸러 내려면 표시 단원의 학년 정보가 필요하다. 검증 방식은 아래 "교육과정 용어표와 금지 목록"을 따른다.

#### 교육과정 용어표와 금지 목록 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_expansion-prep.md` 결정 1 안 A)
- 데이터: `backend/data/curriculum/terms.json` 하나에 교육과정 원문 각 영역의 "용어와 기호"를 학교급(초등·중학·고등)과 영역으로 옮긴다.
  - 원문 근거: 각 영역의 "용어와 기호로 ~를 다룬다" 문장 (교육과정 PDF). 쪽수를 함께 적는다.
  - 중학교 용어마다 처음 다루는 성취기준을 붙인다. 원문에 없는 연결이라 에이전트 추론이고, 사용자 승인을 받는다.
  - 수업용 용어("교수·학습 상황에서 사용할 수 있다")는 따로 표시한다.
  - 용어마다 "코드 검사 제외" 표시를 둘 수 있다 (사용자 결정 2026-11-11). 한국어는 조사가 붙어 낱말 단위로 맞출 수 없어 글자 포함 여부로 찾는데, 일상어(예: 고등 '집합과 명제'의 `조건`, `정의`, `가정`)와 한 글자 용어(예: `항`, `근`, `축`)는 멀쩡한 문장에서도 걸린다. 제외한 용어는 코드 검사는 하지 않고 프롬프트로만 AI에게 피하게 한다. 어느 용어를 뺄지는 용어표 승인 때 근거와 함께 정한다 (일상어 판단 기준은 근거 없음).
- 표시 단원 U의 금지 목록 = 고등학교 용어 전부 + U보다 뒤 단원(학년, 번호 순. 같은 학년 뒤 단원 포함)의 성취기준에 연결된 중학교 용어.
  - 초등 용어와 U 이전·U 안의 중학교 용어는 허용한다.
  - 같은 낱말이 앞 단원과 뒤 단원에 모두 연결되면 앞 단원 기준(허용)으로 본다.
  - 같은 용어가 초등에도 있으면 항상 허용하고, 중학과 고등에 모두 있으면 중학 연결을 따른다.
- 찾는 방법: 글자 포함 여부로 찾는다. 먼저 문장에서 허용 용어(초등, U 이전·U 안의 중학 용어)를 긴 것부터 지운 뒤 금지 용어를 찾는다. 허용 용어 안에 금지 용어가 들어 있어 생기는 오탐(예: 허용 `소인수분해` ⊃ 금지 `인수분해`, 초등 `대각선` ⊃ 금지 `대각`, 초등 `전개도` ⊃ 금지 `전개`)을 막기 위해서다.
- 문제 생성·문제 검사 프롬프트, 코드 검사, 리포트 검증이 모두 이 목록을 쓴다. 개념 JSON의 `not_yet_learned`는 쓰지 않고 코드가 계산한다.
- 한계: 어느 목록에도 없는 수학 용어(교육과정 밖 용어)는 코드가 알아볼 수 없어 AI 검사가 맡는다. 허용 목록 검사를 하지 않는 이유: 목록에 없는 단어가 수학 용어인지 코드가 판단할 방법이 없다 (근거 없음: 한국어 수학 용어 분석기를 찾지 못함).
- 대표 오개념: 에이전트가 출처(교육 연구 자료 등)를 찾아 붙여 초안을 만들고, 사용자가 검토·승인한다. 승인 전 오개념은 출제에 쓰지 않는다. (사용자 결정, 2026-11-09)

#### 개념 데이터 작성 규칙 (반복 생성 실패 대책)
문제 생성·검사가 같은 이유로 반복 실패해 백로그가 쌓인 원인을 개념 데이터 문구로 막는다. 모두 사용자 승인을 받은 규칙이다 (출처: `docs/plans/2026-11-11_units-1-1-2.md`, `docs/plans/2026-11-11_grade1-rest.md`, `docs/plans/2026-11-11_grade2.md`).
- 오개념 판별 항목의 근거
  - 오답 보기 하나에는 오개념 하나만 드러나게 한다.
  - ㄱ, ㄴ, ㄷ을 조합해 고르는 보기는 쓰지 않고, 보기마다 판단 하나(한 학생의 주장이나 식 하나)만 쓴다. 이유: 오개념을 일관되게 적용한 조합이 보기에 없어 검사가 거부한다 (중2 계획 백로그 5건).
  - 다른 사람의 풀이에서 잘못된 까닭을 고르는 문제에서는, 오개념의 내용을 잘못이라고 설명한 보기에 그 오개념을 붙이지 않는다. 그 오개념을 가진 학생은 그 보기를 고르지 않는다 (중2 계획 검토에서 연결 오류 2건).
- 성질 적용 항목의 근거: 고난이도도 학생이 직접 계산·비교해 답을 구한다. 풀이를 다 주고 틀린 단계나 법칙 이름만 고르게 하지 않는다. 고난이도의 "거꾸로 쓰기"는 곱셈·역산으로 되돌려 풀리지 않게 정한다 (예: 몫을 주고 나누어지는 식을 구하는 문제는 내지 않는다).
- 이유 설명 항목의 근거: 구체적인 수나 도형·자료로 설명하게 한다. 문제 문장이 답을 미리 드러내지 않게 한다. 그 단원에서 아직 배우지 않은 문자 일반화·증명은 요구하지 않는다.
  - 중2 도형의 "정당화" 성취기준(`9수03-09·10·11·15`)은 근거를 댄 짧은 정당화(합동·닮음 조건이나 성질을 근거로 고르기, 빠진 근거 채우기, 한두 문장 서술)까지 묻고, 형식을 갖춘 긴 증명은 쓰게 하지 않는다. "가정", "결론" 용어는 쓰지 않는다. 근거: 교육과정 PDF 45~46쪽 해설·고려 사항 (사용자 결정 2026-11-11, 중2 계획 결정 5). 서술형 AI 채점이 짧은 정당화를 안정적으로 채점하는지는 시험하지 않았다.
- 평가 항목 근거에 오개념 ID를 적을 때는 승인된 오개념 문장에 있는 내용만 쓴다. 근거와 오개념 문장이 다르면 생성·검사가 서로 다른 기준을 써 백로그가 반복된다.
- 객관식 평가 항목의 개념에는 승인된 오개념이 최소 1개 연결되어 있어야 한다. 없으면 코드 검사("오답 보기 최소 1개가 승인된 오개념")를 통과할 수 없어 생성이 불가능하다 (중2 계획 `9수02-16-C4`).
- 오개념 문구와 수업용 용어 목록도 용어표 금지 목록과 대조한다. 뒤 단원에 연결된 수업용 용어(예: 중3에 연결된 `이차식`, `전개식`)를 넣으면 코드 검사가 그 용어가 든 문제를 거부한다. 적재 전에 `find_banned_terms`로 문서를 검사한다.
- 오개념 판별 근거에 오개념을 여러 개 적을 때는 "문제마다 이 가운데 하나 이상을 드러내면 되고, 모두 한 문제에 담지 않아도 된다"고 함께 적는다. 이 문장이 없으면 생성·검사가 "모든 오개념을 담아야 한다"로 읽어 백로그가 쌓였다 (중3 1차 계획 백로그 11건 중 다수, `docs/plans/2026-11-12_grade3-part1.md`).
- 고난이도 오개념 판별(`misconception-b`)은 학생의 주장이나 풀이를 판단해야 답이 나오게 한다. 보기는 "옳다/틀리다"와 그 까닭을 함께 쓰고, 두 수의 크기 같은 결과만 맞힌 보기로는 답이 정해지지 않게 한다. 이 형식 예시가 없을 때 같은 칸이 "보기만 확인해도 풀린다"로 6번 거부되었고, 예시를 넣은 뒤 한 번에 통과했다 (`9수01-09`, 2026-11-12).
- 한 개념에 오개념이 하나뿐인 성질 적용 항목은 그 오개념을 어떤 보기에만 붙이는지 근거에 적는다 (예: `9수02-22` "M3는 폭을 반대로 판단한 보기에만 연결"). 적지 않으면 생성 AI가 틀린 보기마다 그 오개념을 붙였고 검사도 통과시켰다 (같은 칸 2번, 2026-11-12 검토에서 발견).
- 그림 평가 항목을 더할 때는 범위 문장의 "그림 없음·묻지 못한다" 문구도 함께 고친다. 남겨 두면 생성 AI가 그림 없이 표로만 문제를 만들어 코드 검사에 모두 거부된다 (`9수04-08` 시험 12번 모두 거부, 2026-11-12).
- 오답을 "몇 가지 차이 중 하나만" 다르게 정할 때는 서로 다른 보기 5개가 실제로 만들어지는지 센다 (`9수02-12` 수직선: 방향 2 × 포함 여부 2 = 4개뿐이라 생성 불가, 2026-11-12).
- 정답이 하나로 정해지지 않는 특수한 경우는 범위에서 막는다 (예: 외심·내심 구별 문제의 정삼각형, 정수를 유한소수로 볼지, 상수의 차수). 원문에서 확인하지 못한 경우는 묻지 않는다.
- 고난이도가 같은 이유로 2번 이상 거부되면 같은 지시로 다시 생성하지 않는다. 거부 이유(백로그 `issues`)를 읽고, 그 평가 항목의 근거에 "이 항목의 고난이도는 어떤 모습인지"를 구체적으로 적은 뒤 생성한다. 적은 문구는 사용자 승인을 받는다 (사용자 결정 2026-11-12, `docs/plans/2026-11-12_hard-guidance-rules.md`).
  - 근거: 같은 지시로 다시 생성하면 같은 이유로 계속 거부되었고, 문구를 적은 뒤에는 통과했다. `9수03-07-C1-정의이해` 15번 거부 → 통과, `9수01-03-C2-오개념판별` 2자리 각 9번 → 모두 통과, `9수02-17-C2-성질적용` 6번 → 통과 (`docs/plans/2026-11-12_figures-rest-grade3.md`).
  - 적는 예: 정의 이해는 "면의 수가 같아도 이름이 다른 입체를 함께 주고 정의의 조건을 따지게 한다"(`9수03-07`), "음수의 부호만 지워서는 풀 수 없게 한다"(`9수01-04`). 성질 적용은 "보기 그림이 모두 주어진 점을 지나게 해 계수를 구해야 답이 나오게 한다"(`9수02-17`), "구할 길이를 미지수로 두고 식을 세워야 풀리게 한다"(`9수03-18`). 오개념 판별은 "한 학생의 주장을 옳다/틀리다 + 까닭으로 판단하고, 각 오개념을 붙일 보기를 정한다"(`9수01-03`, `9수03-04`).
- 그림을 읽는 것이 곧 판단인 항목(산점도 등)의 고난이도 오개념 판별은 "학생 주장을 반박할 근거(그림 속 특정 점·값)를 보기에서 고르게" 하고, 본문과 학생의 말에 그림의 전체 경향을 글로 쓰지 않는다. "몇 개만 보고 판단" 같은 오개념은 "반박할 필요 없이 주장이 옳다" 보기에만 붙이고, 점을 든 오답 보기는 일반 오답으로 둔다. 근거: `9수04-09-C2-오개념판별`이 "그림 해석만 확인해도 풀린다"로 9번 이상 거부된 뒤 이 형식으로 통과 (사용자 결정 2026-11-12).

- 그림을 넣는 기준 (사용자 결정 2026-11-12): **그림이 이해에 조금이라도 도움이 되면 그림을 넣는다.** 사용자는 수학 교육 전문가가 아니므로, 개념 데이터를 쓸 때 에이전트가 평가 항목마다 그림 여부를 근거(교육과정 원문, 교과서에서 그림으로 다루는지, 그림이 있을 때와 없을 때 무엇이 달라지는지)와 함께 제안하고 사용자가 승인한다. 그림은 평가 항목의 `figure`로 정하고 코드가 강제한다 (아래 "그림" 절).
- 그림 종류가 아직 없는 내용 (2026-11-12 기준 도형: 각의 위치, 원, 전개도, 작도)과 이미 승인된 그림 없는 평가 항목은 아래 "그림 없는 문제" 규칙을 따른다.
- 그림 없는 문제 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_grade1-rest.md` 결정 4): 문제에는 글과 KaTeX 수식만 넣는다. 그래서 그림 없이 글과 기호(`∠ABC`, `\overline{AB}`, 좌표)만으로 조건이 모두 주어지는 문제만 낸다. 그래프·표·줄기와 잎 그림은 점의 좌표나 글의 줄로 주고, 작도는 순서와 도구의 쓰임을 글로 묻는다. 그림이 꼭 필요한 내용은 개념 데이터 범위에 "그림 지원 필요"로 적고 문제로 내지 않는다 (목록은 `docs/PROGRESS.md`).
  - 함수 단원 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_grade2.md` 결정 4): 그래프는 식, 지나는 점의 좌표, 표, 글 설명(기울기의 부호, x절편·y절편, 지나는 사분면)으로 준다. 학생이 그래프를 그리게 하지 않는다. 그래프의 모양·위치를 묻는 보기는 글로 쓰고, 식이나 수를 고르는 보기와 서술형도 쓸 수 있다. ("보기 중에서 글로 고르게 한다"고만 쓰면 검사 AI가 모든 보기를 그래프 설명으로 써야 한다고 읽어 거부했다.)
  - 도형 단원: 점의 위치를 "점 D는 `\overline{AB}` 위의 점"처럼 글로 모두 정해 주고, 그림을 보아야만 알 수 있는 조건을 남기지 않는다. 중2 도형(닮음, 평행선과 선분의 비, 피타고라스 정리 포함) 166문제를 검토한 결과 그림이 없어 생긴 결함은 없었다 (2026-11-11).
  - 자료 단원 (사용자 결정 2026-11-11, `docs/plans/2026-11-12_grade3-part1.md` 결정 4): 상자그림은 다섯 수치(최솟값, 제1사분위수, 중앙값, 제3사분위수, 최댓값)를 표나 글로 주고 분포 비교를 묻는다. 산점도는 순서쌍 표나 글 설명(점들이 오른쪽 위로 모여 있음 등)으로 주고 상관관계를 묻는다. 학생이 상자그림·산점도를 그리거나 그림을 눈으로 읽게 하지 않는다. 중3 자료 단원 문제 검토에서 그림이 없어 생긴 결함은 없었다 (2026-11-12).
  - 원과 이차함수 그래프 (시험 결과 2026-11-12, 같은 계획 결정 5): 원 위의 점은 "이 순서로 있다", "현 AB에 대해 같은 쪽에 있다"처럼 순서와 위치를 글로 정하고, 어느 호에 대한 원주각인지 글로 밝힌다. 이차함수 그래프는 함수 단원과 같이 식·꼭짓점·축·볼록한 방향·지나는 사분면으로 준다. 시험 10문제(`9수02-22`, `9수03-19` 일반 변형 1)에서 그림이 없어 생긴 결함은 없었다.
  - 수식 안 한글(예: `$(앞, 뒤)$`)은 KaTeX가 경고만 내고 그대로 렌더링한다 (2026-11-11 확인). `$` 짝이 맞지 않으면 화면이 깨지므로 검토에서 거부한다.

### 그림 (F-05, F-06. 사용자 확정 2026-11-12, `docs/plans/2026-11-12_figures.md` 결정 1~9)
#### 그림 데이터 (`Figure`)
`kind`로 종류를 가른다. 모든 수는 JSON 수, 글은 **일반 글**(KaTeX·HTML 아님, `$`·`<`·`>` 금지, 10자 이하)이다. 화면은 글을 React 텍스트·SVG `<text>`로만 넣는다.

| kind | 필드 | 코드 검사 |
|---|---|---|
| `number_line` 수직선 | `min`, `max`, `tick_step`, `label_step`(눈금 숫자 간격), `points`: [{`x`, `label`, `filled`(●/○, null이면 점만)}], `rays`: [{`from`, `direction`(`left`/`right`), `closed`}], `segments`: [{`from`, `to`, `from_closed`, `to_closed`}] | `min < max`, 눈금 2~25개, 점·끝점이 범위 안, 점 ≤ 8, 반직선+선분 ≤ 3 |
| `coordinate_plane` 좌표평면 | `x_min`, `x_max`, `y_min`, `y_max`, `tick_step`, `show_tick_labels`, `points`: [{`x`, `y`, `label`}], `graphs`: [{`type`(`linear` y=`m`x+`b` / `vertical` x=`c` / `quadratic` y=`a`(x−`p`)²+`q`), 수, `label`}] | 원점이 보이는 창, 눈금 ≤ 25개/축, 점 ≤ 8, 그래프 ≤ 3, `quadratic`은 `a ≠ 0` |
| `bar_chart` 막대그래프 | `categories`(≤ 12), `values`, `y_max`, `y_step`, `x_label`, `y_label` | 개수 같음, 0 ≤ 값 ≤ `y_max` |
| `frequency` 히스토그램·도수분포다각형 | `class_start`, `class_width`, `frequencies`(정수, ≤ 12계급), `show_bars`, `show_polygon`, `y_step`, `x_label`, `y_label` | 둘 중 하나 이상 표시, 도수 ≥ 0 정수 |
| `boxplot` 상자그림 | `axis_min`, `axis_max`, `axis_step`, `series`(1~3): [{`label`, `min`, `q1`, `median`, `q3`, `max`}] | `min ≤ q1 ≤ median ≤ q3 ≤ max`, 축 범위 안 |
| `scatter` 산점도 | `x_min`, `x_max`, `x_step`, `y_min`, `y_max`, `y_step`, `x_label`, `y_label`, `points`(≤ 40): [{`x`, `y`}] | 점이 범위 안 |

- 근거: 첫 범위 그림 종류는 결정 2, 수치로 검사하는 방식은 결정 1. 상한 값은 360px 화면에서 읽을 수 있게 정한 **에이전트 추정**(근거 없음)이며, 시험 생성(단계 5) 뒤 다시 본다.
- OpenAI 구조화 출력: 빈 필드가 없어야 하므로 모든 필드를 두고 쓰지 않는 값은 `null`로 받는다. 종류별 모델의 합집합(`anyOf`)이 SDK 엄격 스키마로 변환되는지 단계 2에서 먼저 시험한다 (`openai` SDK `responses.parse`, `backend/app/ai/providers/openai.py`).

#### 문제·평가 항목
- `Question`·`QuestionDraft`에 `figure: Figure | null`(본문 그림), `Choice`에 `figure: Figure | null`(보기 그림)을 추가한다. 보기 그림이 있는 문제는 보기 5개 모두 같은 `kind`의 그림을 가지며, 보기 글은 비워도 된다.
- 평가 항목(`AssessmentItem`)에 `figure`(`none`/`body`/`choices`, 기본 `none`)와 `figure_kinds`(허용 kind 목록)를 둔다. 코드 검사: `none`이면 그림이 없어야 하고, `body`면 본문 그림이 있어야 하며, `choices`면 보기 그림이 모두 있어야 한다. 그래서 기존 평가 항목에는 그림이 들어가지 않는다.
- 개념 데이터 문서(`docs/concepts/*.md`)에서는 평가 항목 근거 끝에 `[그림: 본문, boxplot]`처럼 적고, JSON으로 옮길 때 두 필드로 바꾼다.
- 금지 용어 검사는 그림의 글(`label`, 축 이름, 범주)에도 한다.

#### 생성·검사 (프롬프트 v8)
- v7을 복사해 그림 절만 더한다: 평가 항목이 그림을 요구할 때만 그림을 넣는다. 그림을 읽어야 답이 나오는 문제는 본문 글에 그림의 수치를 다시 쓰지 않는다. 보기 그림 문제는 보기마다 하나의 판단(예: 볼록한 방향과 꼭짓점이 다른 그래프)이 드러나게 하고, 오개념 연결은 기존 규칙을 따른다.
- AI 검사(v8)는 그림 데이터를 JSON으로 받아 풀고, "그림과 본문·보기·해설이 서로 맞는지"를 확인한다.
- 그림 없는 평가 항목은 v8에서도 v7과 같은 문제를 받도록, v8의 그림 절은 그림 평가 항목에만 채운다.

#### DB (마이그레이션 1개)
- `questions.figure jsonb null`, `question_choices.figure jsonb null`, 둘 다 `jsonb_typeof = 'object'` 검사. 기존 행은 null.

- 진단 API가 학생에게 내려 주는 문제·보기에 `figure`를 더한다. 정답 여부·오개념은 지금처럼 내려 주지 않는다.

#### 화면 (F-06)
- 그리기는 `frontend/src/lib/figures/`의 **프레임워크 없는 TypeScript**(타입만 지우면 실행되는 문법)로 SVG 요소 목록을 만들고, React 부품 `Figure`가 그 목록을 그린다. 같은 코드를 `frontend/scripts/render-figures.ts`가 Node 24(타입 지우기 내장, `node --version` v24.22.0 확인)로 실행해 `review-html`에 SVG를 넣는다. 그래서 검토 화면과 학생 화면의 그림이 같다.
- SVG는 `viewBox`로 그리고 `width: 100%`, 최대 너비를 둔다. `role="img"`와 `aria-label="문제 그림"`.
- 그림 보기: 데스크톱 2열, 600px 미만 1열. 보기 그림 높이 상한.
- 본문 표: 본문을 줄 단위로 보아 머리줄·구분줄(`|---|`)·행이 이어진 부분만 `<table>`로 그린다. 칸은 `$...$` 밖의 `|`로만 나눈다(`$|x|$` 보호). 칸 글은 기존 `MathText`로 그린다. 표는 가로로 넘칠 때만 가로 스크롤.
- 문제별 결과(리포트) 화면에도 같은 부품을 쓴다.

##### C. 새 종류 `geometry` (평면도형)
| 필드 | 내용 |
|---|---|
| `points` | [{`id`(점 이름, 1~3자, 예: A, O, P'), `x`, `y`, `show_name`, `dot`}] ≤ 14. `show_name`이 false면 이름을 그리지 않는다 (작도 흔적용 보조 점) |
| `segments` | [{`from`, `to`, `dashed`, `ticks`(같은 길이 표시 0~3), `parallel_marks`(평행 표시 0~3), `label`}] ≤ 20 |
| `lines` | [{`from`, `through`, `type`(`line` 양쪽으로 / `ray` from에서 through 쪽으로), `dashed`, `parallel_marks`, `label`}] ≤ 6. 그림 창 끝까지 그린다 |
| `polygons` | [{`vertices`(점 id 목록), `shaded`}] ≤ 4. 연한 색 채움 |
| `circles` | [{`center`, `radius`, `dashed`, `points_on`(원 위에 있어야 하는 점 id)}] ≤ 3 |
| `arcs` | [{`center`, `from`, `to`, `trace`(작도 흔적이면 가는 선), `label`}] ≤ 6. from에서 to로 시계 반대 방향 |
| `angles` | [{`vertex`, `from`, `to`, `label`, `right`(직각 표시), `marks`(0이면 보통 각 표시 호 한 겹, 1~3이면 같은 각 표시로 같은 수끼리 크기가 같다)}] ≤ 8. 180°보다 작은 쪽을 그린다 |

- 화면: 좌표에서 그림 범위를 계산하고 x·y 단위를 같게 그린다. 축·눈금은 없다.
- 코드 검사 (허용 오차는 에이전트 추정, 근거 없음): 참조한 점이 있음, id 중복 없음, 좌표 −100~100, 상한. `right`이면 실제 90°±0.5°. 같은 `ticks` 선분은 길이 차 1% 이내, 같은 `marks` 각은 1° 이내, 같은 `parallel_marks`는 방향 차 0.5° 이내. 각의 `label`이 "숫자°"이면 실제 각과 ±3° 이내. 선분 `label`이 숫자 하나이거나 숫자 + 길이 단위(`mm`, `cm`, `m`, `km`)인 것끼리는 (`2x`, `x+1` 같은 식은 제외) (글의 수 ÷ 그려진 길이)의 차이가 5% 이내. `points_on`과 호의 to는 반지름 차 1% 이내.

##### D. 새 종류 `solid` (입체도형)
- 필드: `shape`(`cuboid`, `prism`, `pyramid`, `frustum`, `cylinder`, `cone`, `cone_frustum`, `sphere`, `hemisphere`), `base_sides`(각기둥·각뿔·각뿔대 3~8, 아니면 null), `width`, `depth`, `height`, `radius`, `top_radius`(그리기 비율용 수, 쓰지 않으면 null), `vertex_names`(꼭짓점 이름 목록. 밑면을 시계 반대 방향, 그다음 윗면 순서. 없으면 null), `labels`[{`part`(`width`/`depth`/`height`/`radius`/`top_radius`/`slant`), `text`}], `show_axis`(회전체 축 점선).
- 화면: 정해진 비스듬한 투영(사투영)으로 그리고, 보이지 않는 모서리는 점선. AI는 모양과 치수만 정한다.
  - 숨은 선 판정 (2026-11-12, 남은 그림 항목·중3 계획에서 수정): 각기둥·각뿔·각뿔대는 옆면마다 투영된 방향으로 보이는지 정하고, 밑변은 그 옆면이 안 보일 때, 옆 모서리는 이웃한 두 옆면이 모두 안 보일 때만 점선. 윗면 모서리는 실선. 이전 방식(화면 위치로 정함)은 삼각기둥의 바깥 모서리를 점선, 뒤 모서리를 실선으로 그렸다.
  - 사각뿔(`base_sides` 4)은 직육면체와 같은 사투영(앞 모서리 가로)으로 밑면을 그리고 꼭짓점은 밑면 중심 위. 숨은 꼭짓점은 뒤쪽 하나. 이유: 밑면을 돌리는 방식은 꼭짓점·앞뒤 꼭짓점이 한 세로선에 놓이거나 숨은 모서리가 보이는 모서리에 붙었다. 낮은 각뿔도 읽을 수 있게 최소 세로 높이를 두고(높이 표시가 있으므로 실제 비율보다 커질 수 있다), 높이 표시는 높이선 바로 옆, 글자 크기는 다른 표시와 같다.
- 코드 검사: 모양에 필요한 수는 양수, 나머지는 null, `vertex_names` 개수가 꼭짓점 수와 같음, 가로·세로·높이 비율 5배 이내.

##### E. 새 종류 `net` (전개도)
- 이번에 쓰는 항목은 `9수03-08-C1-이유설명`(원기둥) 하나다. `shape`(`cylinder`, `cone`), `radius`, `height`(원기둥), `slant`(원뿔), `labels`[{`part`, `text`}]. 원기둥은 직사각형 + 위아래 원, 원뿔은 부채꼴 + 원. 부채꼴 중심각은 코드가 반지름·모선으로 계산한다.

- 원문 근거 (방향만): "방정식, 부등식, 함수에 대한 지나치게 복잡한 활용 문제는 다루지 않는다" (교육과정 PDF 37쪽, 중학교 변화와 관계 고려 사항). 평가 방법 (나)의 추론(정당화)·의사소통(표현 간 변환)·연결 역량 (48쪽). 공식 성취수준(상·중·하) 문구는 찾지 못했다. 아래 이해 수준별 조건은 **에이전트 제안, 근거 없음**.

**공통 원칙**
- 같은 평가 항목(개념 × 이해 수준)과 같은 범위 조건 안에서 생각할 거리를 늘린다. 계산 단계 수, 수의 크기, 식의 길이로 어렵게 만들지 않는다.
- 일반: 전형적인 예, 한 가지 표현(식), 정의·성질을 바로 확인하면 풀린다.
- 고난이도: 아래 조건 중 하나 이상을 만족한다. 생성 AI는 사용한 조건을 출력하고, 검사 AI는 그 조건을 실제로 만족하는지로 판정한다. 계산이 짧다는 이유만으로 거절하지 않는다.

| 이해 수준 | 고난이도 조건 (하나 이상) |
|---|---|
| 정의 이해 | (a) 정의의 조건을 하나하나 따져야 판단되는 경계 사례 (b) 일상 언어·표로 주어진 것을 식으로 바꿔 판단 |
| 성질 적용 | (a) 거꾸로 쓰기 (결과가 주어지고 조건을 찾기) (b) 문장·상황을 식으로 바꾼 뒤 적용 (c) 여러 단계 중 어느 단계에서 어떤 성질이 쓰였는지·틀렸는지 판단 |
| 오개념 판별 | (a) 오답 보기가 모두 승인된 오개념 또는 그럴듯한 부분 참에서 나옴 (b) 다른 학생의 주장·풀이의 옳고 그름 판단 |
| 이유 설명 | (a) 모든 경우에 성립하는 이유 설명 (b) 반례로 주장이 틀렸음을 보이기 (c) 두 풀이 방법이 같은 결과를 내는 이유 비교 |

- 다시 볼 조건: 프롬프트 v5 시험에서 hard 항목이 계속 제외되거나, 개발자 검토에서 hard 문제가 일반 문제와 구별되지 않으면 이 정의를 고친다.
- 코드: 조건 표 `backend/app/ai/hard.py` (이 표와 같아야 한다), 프롬프트 `backend/prompts/v5/`.
- 결과 (`docs/plans/2026-11-10_question-bank.md`): v5 hard 시험에서 6개 항목 모두 통과·제외 0 (v4는 1개 제외). `9수02-03` 문제 은행 36자리 생성에서 거절 1건, 백로그 0. 남은 우려: `C4-성질적용` hard("각 단계에서 쓴 성질 고르기")가 일반 문제와 비슷하다는 점. 전문가 검토 때 다시 본다.

### 문제 은행 (사용자 결정, 2026-11-09)
- 문제는 진단할 때 만들지 않고 미리 만들어 둔다. 평가 항목 × 난이도마다 변형 2개 (사용자 결정 2026-11-11, `docs/features.md` F-05).
  - 변형 수는 성취기준 개념 데이터(`backend/data/concepts/<코드>.json`)의 `variants`로 정한다. 없으면 2. 중1 3단원 성취기준 4개(`9수02-01~04`)는 이미 3개로 만들어 `variants: 3`을 둔다.
  - 이유: 남은 성취기준 56개를 변형 3개로 만들면 약 $25로 예산(남은 약 $28.66)과 거의 같다. 2개면 약 $17 (문제당 실측 약 $0.015, `docs/plans/2026-11-11_unit-1-3.md`).
  - 영향: 같은 단원을 세 번째 진단할 때부터 본 문제가 다시 나온다. 출제 규칙(안 본 문제 우선, 모두 봤으면 가장 오래전에 본 문제)은 그대로다. 나중에 늘리려면 `variants`를 올리고 빈 자리만 생성한다.
- 규모 추정: 중1 3단원 120문제 + 남은 성취기준 56개 × 평가 항목 약 5개 × 난이도 2 × 변형 2 ≈ 1,240문제 (평가 항목 수는 중1 3단원 평균 5개에서 나온 값이라 실제와 다를 수 있다)
- 문제 상태: `생성됨` → `검증 통과` → `승인` → (필요하면) `사용 중지`
  - 승인 = AI 검증 통과 + 개발자 확인. 수학 교육 전문가 검토는 실제 학생 공개 전에 한다.
  - 개발자 확인 방식 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_grade1-rest.md` 결정 3): 에이전트가 모든 문제의 정답·오개념 연결·교육과정 범위를 직접 확인하고, 짚을 점이 없는 문제는 승인자 `master`로 바로 승인한다. 짚은 문제만 사용자에게 보여 거부·승인을 받는다. AI 검사(v7)는 오개념 연결 오류를 안정적으로 잡지 못하므로 이 확인을 건너뛰지 않는다.
  - 승인된 문제는 고치지 않는다. 수정이 필요하면 새 문제를 만들고 기존 문제를 `사용 중지`한다. DB 트리거로 막는다 ("DB 스키마" 절).
  - 지금 생성 명령은 검증을 통과한 문제만 저장하므로 `생성됨` 상태는 쓰이지 않는다.
  - 승인자: 승인 명령을 실행할 때 이름을 직접 입력한다 (`--approver`, 사용자 결정 2026-11-10).
- 자리: (평가 항목, 난이도, 변형 1~`variants`). DB는 변형 번호 1~3을 허용한다. 한 자리에 살아 있는(사용 중지가 아닌) 문제는 하나다. 사용 중지하면 그 자리에 새 문제를 만들 수 있다.

### 문제 은행 명령 (F-05, 개발자 전용)
`cd backend` 후 `uv run python -m app.bank <명령>`. 설정은 `backend/.env`에서 프로그램이 읽는다 (Secret key 사용, 개발자 PC에서만 실행).

| 명령 | 하는 일 |
|---|---|
| `convert-concepts <코드>... [--check]` | 승인된 개념 문서를 JSON으로 변환한다. `--check`는 저장하지 않고 기존 파일과 비교한다 |
| `load-curriculum [--dry-run]` | 교육과정 데이터를 DB에 넣는다. 여러 번 실행해도 중복이 없다. JSON에서 빠진 개념·평가 항목·오개념은 지우지 않고 경고만 한다 |
| `generate --standard <코드> [--difficulty normal\|hard] [--item <ID>] (--max-cost-usd N \| --fake) [--dry-run] [--retry-backlog]` | 빈 자리마다 문제를 만들고 검증해 `검증 통과`로 저장. 3번 실패하면 백로그. `--dry-run`은 빈 자리와 최대 비용 추정만 출력. 같은 자리의 다른 변형 본문을 프롬프트에 넘겨 겹치지 않게 한다 |
| `review-html --standard <코드> [--status ...] [--out <경로>]` | 문제·보기·채점 요소·검증 기록·백로그를 HTML 한 파일로 (기본 `experiments/question-bank/`) |
| `approve --approver <이름> <문제 ID>...` | `검증 통과`만 `승인`으로 |
| `disable <문제 ID>...` | `검증 통과`·`승인`을 `사용 중지`로 |
| `backlog --standard <코드>` | 미해결 백로그 목록 |
| `export (--standard <코드> \| --all) --out <파일>` | 문제·보기·채점 요소·오개념 연결·상태·승인 정보·검증 기록·생성 정보와 백로그를 JSON으로 (DB 읽기만) |
| `import <파일>` | 내보낸 JSON을 넣는다. 문제 ID·상태·승인 정보를 그대로 쓴다. 같은 ID가 있으면 내용이 같을 때만 건너뛰고 다르면 실패한다 |

#### 내보내기·가져오기 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_expansion-prep.md` 결정 3)
- 목적: 문제 은행 원본이 개발 DB에만 있다. 백업과 운영 프로젝트 이전에 쓴다.
- 내보낸 파일은 저장소 `backend/data/bank/<성취기준>.json`에 커밋한다. 저장소가 공개라 승인자 값도 공개되며, 사용자가 괜찮다고 정했다 (2026-11-11).
- 비교 기준: 보기·채점 요소의 DB 내부 번호(`rubric_elements.id` 등)는 가져올 때 새로 매겨지므로 내용 비교에서 뺀다. 채점 기록은 채점 요소를 번호(`no`)로 가리키므로 영향이 없다.
- 기존 `bank_insert_question`은 상태를 항상 `validated`로 넣고 ID를 새로 만든다 (`supabase/migrations/20261110173000_create_question_bank.sql`). 그래서 가져오기용 함수 `bank_import_question`을 새 마이그레이션으로 둔다 (`service_role`만 실행).
  1. 받은 ID로 문제를 `validated` 상태로 넣는다.
  2. 보기·채점 요소·오개념 연결을 넣는다 (승인 전이라 `bank_guard_child`가 막지 않는다).
  3. 상태를 받은 값(`approved`·`disabled`)으로 바꾸고 승인자·승인 시각·사용 중지 시각을 넣는다. `bank_guard_question`은 바꾸기 전 상태가 `approved`·`disabled`일 때만 막으므로 이 한 번의 변경은 허용된다.
- 시험은 로컬 Postgres 17 컨테이너로 한다. 원격에 가져오기를 실행하는 것은 운영 프로젝트를 만들 때 따로 확인받는다 (`AGENTS.md` 3.2).

- 실제 AI를 부르는 `generate`는 매번 비용 추정을 보여 주고 사용자 승인을 받은 뒤 실행한다. 호출 기록은 `experiments/question-bank/<시각>/calls.jsonl`.
- 데이터 흐름: `docs/concepts/*.md`(기준, 사용자 승인) → `backend/data/concepts/*.json`(사본) → DB. 성취기준 60개 원문은 `backend/data/curriculum/standards.json`(교육과정 PDF에서 옮김), 표시 단원 23개는 `backend/data/curriculum/display_units.json`(위 연결표). 문서와 JSON을 함께 고친다.
- 진단 중 AI를 쓰는 곳은 서술형 채점(`docs/SCORING.md`)과 리포트 문장 작성("리포트 문장" 절)이다.

### 실패 처리 (사용자 결정, 2026-11-09)
- 검증에 실패한 문제는 그 문제만 다시 만든다. **최대 3번.**
- 3번 모두 실패하면 그 문제 자리를 비워 두고 **백로그**로 남긴다: 평가 항목(개념 ID·이해 수준·난이도), 시도별 실패한 검사와 이유, 시각. 개발자가 나중에 개념 데이터나 프롬프트를 보강하는 데 쓴다.
- 진단할 때 승인된 문제가 하나도 없는 평가 항목은 제외하고 "측정 안 함"으로 처리한다 (`docs/SCORING.md`).

## AI 제공사·모델 (F-05, F-07, F-08)

- **문제 생성·문제 검사·서술형 채점·리포트 문장 모두 OpenAI `gpt-6.1-terra`** (사용자 결정, 2026-11-10). 추론 정도 `reasoning.effort` 기본값 `medium`.
  - 통일한 이유: 문제 생성은 문제 은행을 만들 때 한 번이지만 채점은 학생마다 실행된다. 제공사 하나로 관리한다 (사용자 판단).
- 근거: `gemini-3.8-flash`와 비교 시험 (`docs/plans/2026-11-10_ai-provider-compare.md`, 원본은 `experiments/ai-provider-compare/`, git 제외)
  - 성취기준 9수02-03, 프롬프트 v2, 제공사마다 문제 12개 생성·검사, 서술형 답안 10개 × 3회 채점, 리포트 3세트.
  - 서술형 채점: 두 모델 모두 채점 요소 판정 일치율 100%, 3회 일관성 100%. 오개념 탐지는 Gemini 100%, GPT 90% (한쪽 변만 연산하는 오개념 M2를 놓침).
  - 문제 생성: 통과 문제 16개를 에이전트가 검토했을 때 두 모델 모두 정답 오류·범위 위반 없음. Gemini는 형식 오류(되돌려 달라고 한 ID 값 변경)가 많았다.
  - 1회 비용(표준가)·지연: 생성 GPT $0.0068·14초 / Gemini $0.026·30초, 채점 GPT $0.0018·4초 / Gemini $0.0057·9초.
  - 가격: 입력 $1, 출력 $5 / 100만 토큰, 추론 토큰은 출력으로 청구 ([gpt-6.1-terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra)). 구조화 출력: `client.responses.parse(..., text_format=...)` ([Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)).
  - 한계: 표본이 작다 (성취기준 1개). 기대 판정과 문제 검토는 전문가 검토가 아니다.
- 보완 결과 (프롬프트 v4, `docs/plans/2026-11-10_prompt-v3.md`): 평가 항목 ID·이해 수준·탐지 목록은 코드가 채우고, 채점은 오개념마다 답안 인용과 함께 확인(인용이 답안에 없으면 탐지 제외), 리포트에는 이해도 숫자를 넘기지 않고 내부 ID를 쓰지 않게 했다.
  - v3 재시험 (채점, 답안 15개 × 3회): A05의 M2 3/3, 잘못 탐지 0/21, A03·A08 6/6, 채점 요소 판정 일치 100% (A14 기대값 수정 후), 3회 일관성 100%, 추가 답안 오개념 탐지 14/15.
  - v4 재시험 (생성·리포트): 문제 생성 통과 11/12, 리포트 숫자·내부 ID 0건, 형식 오류 0건.
- 고난이도 거절 문제 (v4 거절 6건 중 5건이 "쉽다"): 프롬프트 v5에서 해결. "고난이도(hard) 정의" 절의 결과 참고.
- 기본 프롬프트: v7 (`backend/app/ai/prompts.py` `PROMPT_VERSION`, 2026-11-11). v7은 v6에서 문제 검사 프롬프트(`review_question.md`)만 바꿨다 ("검증"의 오개념 보기 확인). v1~v6는 기록용. 승인된 문제는 v5(중1 3단원 `9수02-03`)와 v6(`9수02-01·02·04`)로 만들어졌다.
- 프롬프트 v6 (사용자 결정 2026-11-11, `docs/plans/2026-11-11_expansion-prep.md` 결정 2): v5에서 두 가지만 바꾼다.
  - 문제 생성: 채점 요소 설명에 "필수:" 같은 표시를 붙이지 않는다. 필수 여부는 `required` 값으로만 낸다. 코드 검사도 추가한다 ("검증").
  - 리포트: 첫 문장이 단계 이름("~ 단계예요")을 나열하지 않고 학생에게 말하듯 시작한다.
  - 문제 검사·서술형 채점 프롬프트는 v5와 같다.
  - 이미 승인된 v5 문제는 그대로 둔다. 학생 응답의 "필수:" 떼기(`student_description`)도 그대로 둔다.
  - 확인: 실제 AI로 작게 시험한다 (`9수02-03` 문제 몇 개와 리포트 3세트, 문제 은행 DB에 넣지 않음, 비용 승인 후). 판정 기준: 필수 표시로 시작하는 채점 요소 0개, 리포트 첫 문장 단계 이름 나열 0건, 형식 오류 0건.

## 리포트 문장 (F-08)

- 리포트 문장(이해하지 못한 부분, 추정 오개념 설명, 다음 학습 방향)은 **진단마다 AI가 작성**한다. (사용자 결정, 2026-11-09)
- AI는 문장만 쓴다. 이해도 숫자, 단계, 추정 오개념 목록은 `docs/SCORING.md` 계산 결과를 그대로 넘겨받아 쓰고, AI가 바꾸지 않는다.
- 작성한 문장은 `reports`에 저장한다. 다시 열 때 AI를 다시 부르지 않는다 (F-09).
- 리포트 문장도 교육과정 용어 규칙("개념 데이터 (F-03)")을 따른다.

**DB가 지키는 규칙** (문제 은행처럼 트리거와 함수로 지킨다)
- 단계를 제출했거나 진단이 진행 중이 아니면, 그 단계의 답안을 추가·수정할 수 없다 (트리거). F-06 "단계를 제출하면 그 단계 답안은 고칠 수 없다"
- 진단 시작은 함수 `diagnosis_start`가 한 트랜잭션으로 한다 (`service_role`만 실행)
  1. 그 사용자의 만료된 진단을 중단(`expired`)으로 바꾼다
  2. 같은 단원에 진행 중 진단이 있으면, "새로 시작"이 아닐 때는 그 진단 ID를 돌려주고 멈춘다. "새로 시작"이면 기존 진단을 중단(`restarted`)으로 바꾼다
  3. 진단과 출제 항목을 넣는다. 넣는 문제가 모두 `approved`이고 `normal`이며 그 단원의 평가 항목인지 확인하고, 아니면 전체를 취소한다

**접근 권한**: 아래 "접근 권한 (RLS)"을 그대로 따른다
| 대상 | 학생 (`authenticated`) | 백엔드 (`service_role`) |
|---|---|---|
| `diagnoses`, `diagnosis_items`, `answers` | 자기 행 읽기만 | 읽기·추가·수정 |
| `gradings`, `reports` | 자기 행 읽기만 | 읽기·추가 (한 번 저장하면 고치지 않음) |

- 학생이 `diagnosis_items`를 읽어도 정답은 보이지 않는다. 문제 은행 표(정답 여부가 있는 `question_choices`)는 여전히 학생이 읽을 수 없다.
- 삭제 권한은 아무에게도 주지 않는다. 사용자를 지울 때만 연쇄로 지워진다. 탈퇴 방식(F-02)은 결정 대기다.

### 접근 권한 (RLS)
| 대상 | 학생 (authenticated) | 백엔드 (service role) |
|---|---|---|
| `profiles` | 자기 것 읽기 | 쓰기 |
| 진단·출제 문제·답안·채점·리포트 | 자기 것 읽기만 | 쓰기 |
| 교육과정·문제 은행·백로그 | 접근 불가 (권한 회수, 정책 없음) | 읽기·추가·수정 (삭제 권한 없음) |

- 문제 은행을 학생이 직접 읽지 못하게 하는 이유: `question_choices`에 정답 여부가 있다. 문제는 백엔드가 정답을 뺀 상태로 내려 준다.
- 쓰기를 모두 백엔드에서 하는 이유: 제출 시점·단계 진행·채점 결과 조작 방지 (`AGENTS.md` 4.3).
- 정책 작성: 작업(select·insert·update·delete)마다 정책을 따로 두고 `to authenticated`, `(select auth.uid()) = user_id` 형태로 쓰며 `user_id`에 인덱스를 둔다. ([Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security))

## 진단 출제·풀이 (F-04, F-05, F-06. 사용자 승인 2026-11-10)

### 설계 때 확인한 사실 (2026-11-10)
- 승인 문제 36개 중 일반 문제는 18개다 (평가 항목 6 × 변형 3). 1단계는 6문제(객관식 5, 서술형 1)가 된다.
- 문제 본문·보기 191개의 수식 형태 (개발 DB 읽기 전용 조회)
  - 모두 `$...$` 인라인 수식이다. `$$`, `\(`, `\[`, `\$`는 0건이고, `$` 개수가 홀수인 글도 0건이다.
  - 줄바꿈이 있는 글은 23개다.
- 기존 연결 방식: 브라우저 클라이언트 컴포넌트가 Supabase 세션의 access token을 `Authorization: Bearer`로 백엔드에 보낸다 (`frontend/src/app/signup/complete/complete-signup.tsx:15-21`). 진단 API도 같은 방식을 쓴다.

  - **보기 번호 (사용자 결정 2026-11-13):** 라디오 원 대신 CSS 원 번호(③ 모양, 글꼴 글자 ①은 Pretendard에서 작고 위로 붙어 쓰지 않음), 고르면 채움. 실제 라디오는 시각적으로만 숨겨 키보드 선택 유지. 번호 원 세로 가운데 = 보기 첫 글자 세로 가운데 ±2px (E2E `e2e/figures.spec.tsx`). 번호를 없애지 않는 이유: 승인 객관식 1,311개 중 964개의 해설이 ①②로 보기를 가리킴. 판 안 본문은 테두리 상자, "답을 골라요"는 시각적으로만 숨김

  - 서술형은 입력을 멈추고 1초 뒤, 그리고 화면을 떠나기 전에 저장한다. 1초는 근거 없음
  - 저장 상태를 표시한다 ("저장 중…" / "저장됨" / "저장하지 못했어요" + "다시 시도")
  - 지금 문제에 답하기 전에는 "다음"이 꺼져 있고 "답을 고르면(쓰면) 다음 문제로 넘어갈 수 있어요"를 보인다. "답함" 기준은 제출 조건과 같다 (번호를 골랐거나 공백을 뺀 서술형 답이 1자 이상). "이전"은 언제든 누를 수 있다 (사용자 결정 2026-11-11)
  - 제출 버튼은 그 단계의 마지막 문제에서 "다음" 자리에만 보이고, 모든 문제에 답하면 켜진다. 제출 전에 한 번 확인한다 (사용자 결정 2026-11-11, 수동 확인에서 요청)
  - 제출 후에는 답을 바꿀 수 없고 "제출했어요. 채점 기능은 준비 중이에요"를 보인다
  - 중단된 진단은 "기간이 지나 중단된 진단이에요" 등을 보인다
- 터치 대상: 버튼과 보기의 최소 높이는 44px. 근거: WCAG 2.2 Target Size (Enhanced) 2.5.5의 44×44 CSS px ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)). 최소 기준(2.5.8)은 24px이다.

### 수식 렌더링 부품
- 보기 수식은 가로로 넘칠 때만 가로 스크롤한다. `overflow-x: auto`만 주면 세로도 `auto`가 되어 `\dfrac` 분수에 세로 스크롤 막대가 생기므로(2026-11-11 사용자 수동 확인), 세로로는 넘치지 않게 한다. 분수 표기(`\dfrac`)는 바꾸지 않는다 (사용자 지시).
- 글을 `$...$` 기준으로 나눠 수식 부분만 `katex.renderToString(…, { throwOnError: true })`로 그린다. 나머지 글은 React 텍스트로 넣어 HTML로 해석되지 않게 한다.
  - KaTeX 기본값은 `trust: false`라 `\href` 같은 명령을 막는다 ([KaTeX Options](https://katex.org/docs/options)).
- 줄바꿈은 그대로 보이게 한다 (`white-space: pre-line`). 본문 23개에 줄바꿈이 있다.
- 렌더 오류가 나면 원래 글을 그대로 보이고 오류 표시를 한다. 화면 전체가 깨지지 않게 하려는 것이다.
- `$$` 별도 줄 수식은 지금 데이터에 없다. 지원하지 않고, 나오면 렌더 오류로 처리한다. 쓰게 되면 `docs/DESIGN.md` "수식 렌더링"의 줄바꿈 CSS와 함께 추가한다.
- 승인 문제 렌더 확인은 일회성 실행으로 하고, 문제 원문을 저장소에 넣지 않는다.

## 채점·2단계·리포트 (F-05 2단계, F-06, F-07, F-08, F-09. 사용자 승인 2026-11-10)

결정 (사용자 결정 2026-11-10, 모두 에이전트 추천 채택): 제출 요청 안에서 바로 채점하고 AI 실패 시 아무것도 기록하지 않는다 / 2단계는 1단계와 같은 출제 규칙 / 리포트는 진단이 끝날 때 만들고 실패하면 열 때 다시 / 2단계 도중 중단 리포트는 처음 열 때 / 리포트의 배우지 않은 용어는 JSON, 나머지는 DB / E2E는 `AI_MODE=fake` / 사용자별 AI 호출 제한은 학생 공개 전 / 끝난 진단은 같은 주소에서 리포트와 문제별 결과.

### DB 규칙 (함수 하나가 한 트랜잭션으로 처리, `service_role`만 실행)
- `diagnosis_submit_stage1(user, diagnosis, gradings jsonb, stage2_question_ids uuid[])` — 기존 함수를 바꾼다.
  1. 진단 행을 잠근다. 진행 중이 아니거나 답하지 않은 문제가 있으면 지금처럼 결과 코드를 돌려준다.
  2. 1단계 항목 **모두**에 채점을 넣는다. 빠지거나 남는 항목이 있으면 전체를 취소한다.
  3. 2단계 문제가 있으면:
     - 각 문제가 승인된 고난이도이고, **1단계에서 통과한 평가 항목**의 문제인지 확인한다. 아니면 전체를 취소한다.
     - 2단계 항목을 넣고 `stage2`로 바꾼다.
  4. 2단계 문제가 없으면 `completed`로 바꾼다.
- `diagnosis_submit_stage2(user, diagnosis, gradings jsonb)`: 2단계 항목 모두에 채점을 넣고, `stage2_submitted_at`을 기록하고, `completed`로 바꾼다.
- `report_create(user, diagnosis, gradings jsonb, report jsonb)`
  - 2단계 도중 중단된 진단이면, 2단계에서 답한 문제의 채점을 함께 넣는다 (F-06 "답한 문제까지로 채점").
  - 1단계 도중 중단된 진단과 진행 중인 진단에는 리포트를 만들지 않는다.
  - 이미 리포트가 있으면 아무것도 바꾸지 않는다.
- 만료: 시작 후 3일이 지난 `stage1`·`stage2` 진단을 중단으로 바꾼다.
  - 지난 계획에서 넣은 "1단계 제출한 진단 제외"는 뺀다. 이제 제출과 채점이 한 번에 처리되므로, 제출했는데 `stage1`로 남는 상태가 없다.
- `answers_guard`는 바꾸지 않는다. 2단계를 제출하면 `completed`가 되므로 지금 규칙으로 막힌다.

| `POST /diagnoses/{id}/stages/2/submit` | 2단계 채점 → 완료 → 리포트 시도 → `{status: 'completed'}` | 404, 409, 503 |
| `GET /diagnoses/{id}` | 지금처럼 하되, 2단계 문제를 포함한다. 진단이 끝났으면(완료, 또는 2단계에서 중단) 문제마다 결과를 붙인다: 맞음/틀림·통과, 객관식 정답 번호, 해설, 서술형 모범 답안과 요소별 충족 이유 | — |
| `GET /diagnoses/{id}/report` | 있으면 돌려주고, 없으면 만든다 (2단계 도중 중단 채점 포함) | 404, 409 `no_report`(1단계 도중 중단·진행 중), 503 `report_failed` |

- **리포트 응답:** 단원 단계, 개념별(이름·단계·표시·추정 오개념 내용), 리포트 문장.
  - 이해도 숫자와 내부 ID(개념·오개념 ID)는 응답에 넣지 않는다 (`docs/SCORING.md` 5절).
  - 단계 기준을 정하는 데 숫자가 필요하면 서버에서만 쓴다.
- 문제별 결과도 진단이 끝난 뒤에만 준다. 진행 중에는 정답·해설을 지금처럼 내려 주지 않는다.

### 화면 (`/diagnoses/[id]`, 기존 풀이 화면 확장)
- **제출 중:** "채점하고 있어요"를 보이고 버튼을 막는다.
- **2단계로 넘어갈 때:** "기본 문제를 잘 풀었어요. 심화 문제 N개를 풀어 볼까요?" 안내 후, 2단계 문제를 같은 방식(한 문제씩, 자동 저장, 제출)으로 푼다.
- **503일 때:** "채점을 하지 못했어요. 잠시 후 다시 제출해 주세요" (답은 그대로).
- **완료 뒤:**
  - 리포트를 보인다: 단원 단계, 개념별 단계, 이해하지 못한 부분, 추정 오개념("~일 수 있어요"), 다음 학습 방향.
  - 아래에 문제별 결과를 보인다: 내 답, 맞음/틀림, 해설.
  - 리포트를 만드는 동안 "리포트를 쓰고 있어요"를 보인다. 실패하면 "다시 시도" 버튼을 둔다.
- 안내와 버튼은 화면 안에 보인다 (`toBeInViewport`).

### 구현하며 정한 것 (2026-11-10, `docs/plans/2026-11-10_grading-report.md`)
- **채점 중 답안 변경:** 채점(AI 약 4초) 사이에 답이 바뀌면 저장한 채점과 답이 어긋난다 (F-09 "당시 내용 그대로").
  - 채점 결과마다 채점에 쓴 답안의 `answer_updated_at`을 DB 함수에 넘긴다.
  - 세 함수(`diagnosis_submit_stage1`, `diagnosis_submit_stage2`, `report_create`)가 진단 행을 잠근 뒤 지금 `answers.updated_at`과 비교한다. 다르면 아무것도 쓰지 않고 `answers_changed`를 돌려준다.
  - 백엔드는 409 `answers_changed`, 화면은 "답이 바뀌었어요. 다시 제출해 주세요"를 보이고 진단을 다시 읽는다.
- **"필수:" 표시:** 승인 문제 채점 요소 14개 중 10개가 "필수:"로 시작한다 (생성 프롬프트 문제, `docs/PROGRESS.md`). 승인된 문제는 고치지 않으므로 학생용 응답에서만 앞의 "필수:", "(필수)", "[필수]"를 뗀다 (`student_description`).
- **로그:** uvicorn은 자기 로거만 설정하므로, 앱 시작 때 `app` 로거의 INFO를 표준 오류로 내보낸다 (`configure_app_logging`).
  - AI 호출 로그: 모델, 토큰, 지연, 비용, 성공 여부만 남긴다. 답안·리포트 문장은 남기지 않는다.
  - 채점·리포트 실패: 진단 ID와 예외만 남긴다.
  - `AI_MODE=fake`면 시작 때 경고를 남긴다.
- **"출제할 때 AI를 호출하지 않는다" 확인 방법 (F-05):** 진단 패키지에 AI 채점이 들어오면서, import 금지 검사는 출제 코드(`selection.py`)로 좁혔다. 대신 "진단 시작 요청은 AI를 0번 부른다"는 동작 테스트를 둔다.

### API: `GET /diagnoses?limit=&before=` (로그인 필요)
- 브라우저가 Supabase를 직접 읽지 않고 백엔드를 거친다 (다른 진단 화면과 같음). 다른 진단 API처럼 먼저 그 사용자의 만료된 진단을 중단으로 바꾼다. 가입 미완료는 403.
- 백엔드는 Secret key로 읽어 RLS를 거치지 않으므로, 코드에서 `user_id`로 직접 거른다.
- 순서: 시작 시각 최근 순, 같으면 ID 순. `limit` 기본 20, 1~50 (밖이면 422). `before`는 직전 쪽 마지막 진단의 (시작 시각, ID)로, 그 뒤 진단을 준다. 빠지거나 겹치는 진단이 없어야 한다.
  - 20개씩 나누는 이유: 시험 계정 A·B의 기록은 지우지 않고 쌓인다 ("로그인 흐름 E2E"). 20은 근거 없음.
- 항목: 진단 ID, 상태, 중단 이유, 시작·1단계 제출·완료·중단 시각, 단원(학년, 이름, 출판사). 그리고 다음 쪽 기준(없으면 비움). `stage1_submitted_at`은 1단계 제출 전 중단 여부를 구별한다 (사용자 결정 2026-11-13).
- 넣지 않는 것: 이해도 숫자, 점수, 문제 내용, 내부 ID(개념·오개념) (`docs/SCORING.md` 5절과 같은 원칙).
- DB 변경 없음. `diagnoses_user_id_idx`를 쓴다.

### 화면: `/history`
- 공통 머리말(900px 이상은 사이드바)에 "지난 기록" 링크. 진단 화면의 "지난 기록으로" 링크는 머리말과 겹쳐 뺐다 (2026-11-13).

## 인증 (F-01)

`docs/plans/2026-11-09_skeleton-login.md`에서 구현하며 정한 것.

### 흐름
- 가입·로그인: 이메일 + 비밀번호, 카카오 (Supabase Auth). 두 방식 모두 `/auth/callback` → `/signup/complete` → 백엔드 `POST /signup/complete`를 거친다.
- **F-11 자리**: 백엔드 `backend/app/profiles.py`의 `check_signup_requirements` (가입 완료 직전 호출, 지금은 그대로 통과). 연령 확인·보호자 동의는 여기에 넣는다.

### 프론트엔드
- `@supabase/ssr`로 서버·브라우저 클라이언트 ([Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client)). 서버 코드는 `getClaims()`로 확인하고 `getSession()`을 믿지 않는다.
- 보호 규칙 두 겹
  - 주소 (사용자 결정 2026-11-12): 로그아웃 `/` = 랜딩(`proxy.ts`가 `/landing`으로 rewrite, 주소는 `/`), `/login` = 로그인 카드, 로그인 `/` = 학습 지도, `/landing` 직접 접근은 `/`로.
  - `src/proxy.ts` (Next.js 16): 로그인 여부만. 응답에 `Cache-Control: private, no-store` (갱신된 세션 쿠키가 공유 캐시로 다른 사용자에게 가지 않게, 같은 문서).
  - `src/app/(protected)/layout.tsx`: 자기 `profiles` 행(RLS)으로 가입 완료 여부 확인, 미완료면 `/signup/complete`.

### 백엔드
- 토큰 검증: 프로젝트가 ES256 비대칭 서명을 쓴다 (`/auth/v1/.well-known/jwks.json` 확인). PyJWT `PyJWKClient`로 공개 키를 받아 직접 검증한다. ES256만, `aud=authenticated`, `iss=<SUPABASE_URL>/auth/v1`, `exp`·`sub` 필수 ([JWT Signing Keys](https://supabase.com/docs/guides/auth/signing-keys)).
- 시각 허용 오차 10초 (`CLOCK_SKEW_SECONDS`, 사용자 결정 2026-11-11): `exp`·`iat`를 볼 때 서버 시계 차이 10초까지 봐준다. JWT 명세가 작은 허용 오차를 허락한다 ([RFC 7519 4.1.4](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.4)). 서명 검사는 그대로라 위조를 허용하지 않는다. 계기: PC 시계가 2초 늦어 막 발급된 토큰이 `iat` 미래로 401 (`docs/TEST_LOG.md` 2026-11-11, 2회). 10초는 근거 없음.
- DB 쓰기: supabase-py + Secret key(`sb_secret_`). 클라이언트는 프로세스당 하나.
- CORS: `FRONTEND_ORIGIN`에 적은 주소만 허용(쉼표로 여러 개, 각 끝 `/` 제거, `Settings.cors_origins`), 쿠키 미사용.

### 개발 중 같은 와이파이의 폰에서 접속 (사용자 결정, 2026-11-10)
- 개발용이다. 이메일 + 비밀번호 로그인만 대상이고 카카오 로그인은 뺀다 (사용자 지시). Supabase 설정은 바꾸지 않는다.

  | 막히던 곳 | 설정 |

- `pnpm test:e2e:dev`는 백엔드 주소를 `http://localhost:8000`으로 고정해 이 설정과 상관없이 돈다 (`frontend/playwright.dev.config.ts`).

### 카카오 로그인 설정
- Supabase는 카카오에 항상 `account_email profile_image profile_nickname`을 요청한다 (2026-11-10 Supabase 인가 주소에서 확인). 카카오 동의항목에서 이 세 항목을 모두 켜지 않으면 KOE205 에러가 난다.
- `account_email`은 비즈 앱에서만 켤 수 있다. 개인 개발자는 앱 아이콘 등록 + 본인인증 + 카카오비즈니스 약관 동의로 비즈 앱 전환이 가능하다 (사용자 확인).
- 이메일·프로필 사진은 **선택 동의**로 둔다 (`AGENTS.md` 4.3 최소 수집). 동의한 값은 Supabase Auth 사용자 정보에 저장되므로 개인정보 처리방침에 포함해야 한다 (`docs/PROGRESS.md` 공개 전 필수 항목).

- **테마 `concept`** (`frontend/src/themes/concept/conceptTheme.ts`): stone을 `extends`하고 아래만 바꾼다. 사용자가 임시 미리보기에서 7개 테마와 섞은 안을 보고 "stone+neutral글꼴"을 고름.
  - 글꼴: 본문·제목 모두 Pretendard(저장소 `public/fonts/pretendard/`), 코드는 시스템 고정폭. stone의 `fonts.css`는 Google Fonts를 불러오므로 쓰지 않는다 (사용자 결정 "글꼴은 모두 Pretendard", 외부 요청 0개를 E2E로 검사).
  - 글자 크기: `typography.scale {base: 16, ratio: 1.2225}`. stone은 데스크톱 14px·터치 16px이라 데스크톱 글자가 작았음 (사용자 지적 2026-11-13).
  - 컨트롤 높이: `--size-element-md/lg` 44px. Astryx 기본 32·36px은 터치 기준 44px(위 "화면", WCAG 2.5.5) 미달.
  - `astryx theme build` → `theme add concept` → `theme use concept`로 빌드한 테마를 쓴다(런타임 테마는 SSR에서 깜빡임, `astryx docs use-a-theme`). 생성 파일(`src/astryx-themes.ts`, `src/themes/concept/concept.{js,css,d.ts}`)은 손대지 않고 `.prettierignore`에 둔다(Prettier가 바꾸면 `astryx doctor` 실패). 설명 파일 `conceptTheme.doc.mjs`는 CLI가 쓰므로 두고 ESLint 대상에서만 뺀다(사용자 결정).
- **CSS:** `@astryxdesign/core/reset.css`·`astryx.css`·테마 CSS는 `@layer` 안에 있다. `globals.css`는 layer 밖이라 항상 이기므로 Astryx 컴포넌트를 덮는 태그 전체 규칙을 두지 않는다. `globals.css`의 색·간격·모서리는 Astryx 토큰(`--color-*`, `--radius-*`, `--size-element-*` 등)만 쓴다.
- **다크·라이트 전환:** 기본은 시스템. 머리말 해·달 버튼이 `localStorage.theme`에 저장하고, `next/script` `beforeInteractive` 스크립트가 그리기 전에 `<html data-theme>`를 설정한다. Astryx 최상위 `<Theme mode>`가 `<html data-theme>`를 관리하므로 모드는 `localStorage`에서 읽는다(`theme-button.tsx` `storedTheme()`).
- **로그인·가입 폼:** 입력창과 제출 버튼은 기본 HTML 요소로 둔다. Astryx `Button`으로는 스크립트 실행 전 진짜 `disabled`를 보장할 수 없어서다(`AGENTS.md` 4.3). 모양은 Astryx 토큰으로 맞춘다.
- **리포트 표시** (`report-summary.tsx`): 단원·개념 단계를 Badge(글자) + 3칸 ProgressBar로. 숫자("3단계 중 N단계" 등)는 보이지 않는다(`docs/SCORING.md` 5절). 랜딩의 "샘플 리포트"가 같은 컴포넌트에 `9수02-03` 예시 데이터를 넣어 쓴다.
- **캐릭터 "개념이"** (`src/components/mascot.tsx`, 사용자 요청 2026-11-13): 수학 개념을 확인하는 학생 모습 SVG, 테마 토큰 색. 생각 중(로딩·리포트 작성), 쉬는 중(1단계 도중 중단된 진단), 반가움(지난 기록 없음). `StatusScreen`(Astryx `EmptyState` icon 칸)으로 제목·설명·다음 행동과 함께 쓴다. `prefers-reduced-motion`이면 멈춘다. 장식이라 화면 읽기에서 숨긴다.
- **브라우저 지원:** Astryx는 CSS anchor positioning·`light-dark()`·Popover API를 쓴다 (`astryx docs browser-support`). 학생 기기 범위는 `docs/PROGRESS.md` 공개 전 확인 항목.


### 화면 스타일 기준 (UI 고도화 2차에서 굳힘, `docs/plans/2026-11-13_ui-polish-2.md`)
다음 화면(F-02 `/account` 등)은 아래 규칙을 그대로 따른다.

- **강조색 보라** (사용자 결정 2026-11-13): 라이트 `#6744c5`(흰 글자 6.54:1), 다크 `#aa9cf7`(어두운 글자 `#101018` 7.94:1). 테마 `concept`의 `--color-accent`·`--color-on-accent`·`--color-text-accent`·`--color-icon-accent`·`--color-accent-muted`로만 쓴다(`src/themes/concept/conceptTheme.ts`). 화면 코드에 색 값을 직접 쓰지 않는다(문제 판 제외).
- **구역 나누기** (사용자 확정 2026-11-13 항목 5): 페이지 구역은 제목 + 간격으로 나눈다. 함께 다루는 묶음만 `Card`로 감싼다. 강조 구역은 한 화면에 하나만 연한 바탕(회색 또는 `--color-accent-muted`)으로 둔다.
- **그림자** (사용자 지적 2회 "과하다"): 누르는 모양을 위한 아래 두께 그림자는 2px 이하, 다크는 더 옅게. 고른 항목의 빛은 `--color-accent-muted`로 은은하게.
- **색만으로 뜻을 전하지 않는다** (WCAG 1.4.1): 상태는 색 + 아이콘·글자. 예: 결과 보기 테두리 색 + "✓ 정답"/"✗ 내 답"(문제 판 안, 고정 색), 학습 경로 노드 색 + SVG 아이콘 + `aria-label`.
- **아이콘**: 이모지를 쓰지 않고 직접 그린 SVG(선 두께 2, `currentColor`, `aria-hidden`)를 쓴다(`home-actions.tsx`, `learning-map.tsx`).
- **화면 틀** (사용자 결정 2026-11-14): 로그인 뒤 화면은 900px 이상에서 왼쪽 사이드바(브랜드, 학습하기 `/`, 지난 기록 `/history`, 테마 전환, 로그아웃, 현재 페이지 `aria-current="page"`), 900px 미만에서는 머리말. 폰 머리말은 동작마다 아이콘 Button 하나(글자는 숨기고 `label`로 이름). 없는 기능(랭킹, 학습 현황 등)은 메뉴에 넣지 않는다.
- **학습 지도** (사용자 결정 2026-11-14, 사용자 시안 그림 기준): 학년 탭 → 진도 요약("중N · M단원 중 K개 정복", 막대, "K / M") → 왼쪽 학습 경로 + 오른쪽 단원 내용(sticky). 900px 미만은 단원 내용이 아래에서 올라오는 시트(닫기 버튼·Escape).
  - 경로: 점 격자 바탕, 둥근 네모 노드(데스크톱 64px, 폰 56px)를 곡선으로 잇고, 노드 옆에 알약 이름 칩, 아래에 범례.
  - 노드 상태(`src/lib/unit-progress.ts`): 정복=강조색 채움+체크, 완료=진한 회색+체크, 기본 이해=경고색+반 채운 원, 다시 도전=오류색+회전 화살표, 진행 중=강조색 두꺼운 테두리+▶, 시작 전·준비 중=회색+번호(준비 중은 더 흐리게).
  - **순서 잠금·자물쇠 없음, "다음 단원" 추천 없음**: 단원은 서로 독립된 자가 진단이라 어느 단원이든 언제든 시작한다(사용자 "이전 단원 완료해야 다음 단원을 진행하는 그런 시스템은 아니야"). 개념이는 학습 지도에 두지 않는다.
