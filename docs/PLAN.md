## 이전 계획에서 이어받은 것
- **실제 문제 생성은 OpenAI API(`gpt-6.1-terra`)로 하고, 사용자가 허락하기 전까지 절대 실행하지 않는다** (사용자 지시 2026-11-11).
  - 계획 승인은 실행 허락이 아니다.
  - 성취기준마다 `--dry-run`으로 빈 자리와 비용 추정을 보여 주고, "실행해"를 받은 뒤 실행한다.
  - (출처: plans/2026-11-11_expansion-prep.md 인계, `docs/DESIGN.md` "문제 은행 명령")
- **예산 (사용자, 2026-11-11): OpenAI 충전액은 $30뿐이다. 아껴 쓴다.** 비용 추정을 보여 줄 때 누적 사용액과 남은 예산을 함께 적는다. 전체 문제 은행 추정(약 $28)이 예산과 거의 같으므로, 비용을 줄일 방법도 함께 검토한다 (진행 메모).
- 비용 참고: v6 실측 문제 1개(생성 + 검사 + 재시도) 약 $0.013. 금지 목록 때문에 생성 입력이 평균 약 3,400토큰이다. (출처: 같은 인계)
- 새 개념 데이터에는 `not_yet_learned`를 쓰지 않는다. 금지 목록은 용어표에서 자동 계산된다. (출처: 같은 인계)
- 개념 데이터 원칙 (`docs/DESIGN.md` "개념 데이터 (F-03)")
  - 개념은 잘게 나눈다 (사용자 결정 2026-11-09).
  - 평가 항목 근거는 "성취기준 문장의 어느 표현"인지 "에이전트 추가(이유)"인지 구분해 적는다.
  - 대표 오개념은 에이전트가 출처를 찾아 붙이고 사용자가 승인한다. 승인 전 오개념은 출제에 쓰지 않는다.
  - 사용자는 수학 교육 전문가가 아니다. 근거가 약한 항목은 "전문가 검토 필요"로 표시하고, 수학적으로 맞는지 판단을 사용자에게 떠넘기지 않는다.
- `scope_note`(범위 조건)가 성취기준의 핵심 내용을 막지 않는지 확인한다. `9수02-03`에서는 "일차식·일차방정식만"이라는 문구가 항등식·수로만 된 등식을 막아 고친 적이 있다. (출처: plans/2026-11-10_prompt-v3.md 인계)
- 데이터 흐름: `docs/concepts/<코드>.md`(사용자 승인 원본) → `backend/data/concepts/<코드>.json`(사본) → `load-curriculum`으로 DB. 문서와 JSON을 함께 고친다. (`docs/DESIGN.md` "문제 은행 명령")
- 승인한 문제는 `bank export --standard <코드> --out backend/data/bank/<코드>.json`으로 내보내 커밋한다. (출처: plans/2026-11-11_expansion-prep.md 인계)
- 고난이도(hard) 정의는 잠정 기준이다. hard가 계속 제외되거나 일반 문제와 구별되지 않으면 정의를 고친다 (`docs/DESIGN.md` "고난이도(hard) 정의").
- 원격 쓰기: `load-curriculum`, `generate`, `approve`는 개발 프로젝트 DB에 쓴다. `load-curriculum`도 원격 데이터 변경이므로 실행 전에 확인받는다 (`AGENTS.md` 3.2).
- 위임: Codex·Cursor는 Herdr pane(`w9:pQ`, `w9:pR`)에서 실행한다. 이번 계획은 대부분 데이터 작업이라 코드 위임이 적다. (출처: plans/2026-11-11_history.md 인계)

## 결정 사항 (사용자 결정, 2026-11-11: "추천대로 진행해라")
결정 1은 안 B, 결정 2는 추천안(세 성취기준 한 번에 승인)을 채택한다. 결정 3은 확인 사항이다.

1. **개발자 확인 방식** (승인 = AI 검증 통과 + 개발자 확인, F-05)
   - 규모: 이번 단원만 약 100문제(성취기준 3 × 평가 항목 약 6 × 난이도 2 × 변형 3), 전체로는 약 2,100문제.
   - 안 A: **전부 확인.** 검토용 HTML(`review-html`)로 모든 문제를 보고 승인한다. 전체로 가면 사람 시간이 가장 많이 든다.
   - 안 B (추천): **이번 단원은 전부 확인하고, 확인하며 찾은 문제 유형을 기록한다.** 그 기록으로 다음 단원부터 표본 확인으로 줄일지 정한다.
     - 이유: AI 검증(코드 검사 + AI 검사)이 놓치는 문제가 얼마나 되는지 아직 자료가 없다. `9수02-03`에서는 36개 중 1개를 사용자가 거부해 사용 중지했다 (plans/2026-11-10_question-bank.md 인계). 표본으로 줄일 근거가 부족하다.
   - 안 C: 처음부터 표본 확인 (예: 평가 항목마다 1개). 근거 없음.
   - 참고
     - 개발자 확인은 "학생에게 내보내도 될 만큼 명백한 오류·이상이 없는가"를 본다. 수학 교육 관점의 검토는 학생 공개 전 전문가 검토로 한다 (`docs/PROGRESS.md` 공개 전 필수 항목).
     - 에이전트가 HTML과 함께 문제마다 짚을 점을 정리해 확인을 돕는다.
2. **개념 데이터 작업 순서**
   - 추천: 세 성취기준의 개념 데이터 초안을 한 번에 만들어 한 번에 승인받는다. 생성은 성취기준마다 비용 승인을 받고 실행한다.
     - 이유: 세 성취기준이 서로 이어진다(문자식 → 일차식 계산 → 일차방정식). 개념 경계와 범위 조건을 함께 봐야 겹치거나 빠지는 게 없다.
   - 다른 안: 성취기준 하나씩 데이터 → 생성 → 승인을 반복한다. 승인 대기가 세 번 생긴다.
3. **단원 진단 길이** (확인 필요 사항)
   - 네 성취기준이 모두 차면 1단계 문제 수가 평가 항목 수만큼(약 24문제) 늘어난다. 2단계는 통과한 항목만큼 더 나온다 (F-05 "1단계: 선택한 표시 단원의 모든 평가 항목에 일반 문제").
   - 이번 계획에서는 F-05를 바꾸지 않는다. 5단계에서 실제 문제 수와 풀이 시간을 확인하고, 너무 길면 F-05 변경을 사용자에게 제안한다. 길이 기준은 근거 없음.

## 단계
1. **개념 데이터 초안** (Opus)
   - 교육과정 PDF의 성취기준 해설·고려 사항을 근거로 세 성취기준의 개념, 평가 항목, 범위 조건, 용어를 정한다.
   - 대표 오개념은 출처(교육 연구 자료)를 찾아 붙인다. 찾지 못하면 "출처 없음 — 전문가 검토 필요"로 표시한다.
   - `docs/concepts/9수02-01.md`, `9수02-02.md`, `9수02-04.md`를 작성한다.
   - 함께 확인: 용어표(`terms.json`)에서 세 성취기준에 연결된 용어가 맞는지 보고, 다르면 고칠 안을 함께 낸다.
   - 완료 조건: **사용자 승인**.
2. **JSON 사본과 DB 적재** (Opus 또는 Cursor)
   - `backend/data/concepts/*.json`을 작성하고 pytest(개념 데이터 형식 검사)를 통과시킨다.
   - `load-curriculum --dry-run`으로 바뀌는 내용을 보여 주고, 확인받은 뒤 개발 DB에 적재한다.
   - 완료 조건: 원격 조회로 개념·평가 항목·오개념 수 확인.
3. **문제 생성** (Opus, 성취기준마다 반복)
   - `generate --dry-run`으로 빈 자리와 최대 비용 추정 → **사용자 "실행해"** → 실행.
   - 결과로 통과·재시도·백로그·실제 비용을 보고한다.
   - 백로그가 생기면 원인을 분석하고 개념 데이터나 범위 조건 보강을 제안한다. 다시 생성할 때도 비용 승인을 받는다.
   - 완료 조건: 모든 자리가 채워지거나, 남은 백로그의 원인과 처리 방안이 정해졌다.
4. **검토와 승인** (사용자 + Opus)
   - `review-html`로 검토용 HTML을 만들고, 에이전트가 문제마다 짚을 점(정답 근거, 범위, 용어, 고난이도 조건)을 정리한다.
   - 사용자가 확인하면 `approve --approver <이름>`으로 승인한다. 거부한 문제는 `disable`한 뒤 그 자리를 다시 생성한다 (비용 승인).
   - 결정 1이 안 B면, 확인하며 찾은 문제 유형을 진행 메모에 기록한다.
   - 완료 조건: 단원 상태가 "전체"다 (`GET /units`).
5. **내보내기와 진단 확인**
   - `bank export`로 세 성취기준 파일을 만들어 커밋한다.
   - 로그인 흐름 E2E(`pnpm test:e2e:dev`)는 `AI_MODE=fake`로 이 단원을 시작한다. 늘어난 문제 수로도 통과하는지 확인한다.
   - 사용자 수동 확인: 이 단원 진단을 한 번 끝까지 푼다 (1단계 문제 수, 걸린 시간, 리포트). 실제 AI 채점·리포트를 쓸지는 그때 비용과 함께 묻는다.
6. **검수와 계획 종료** — 5.3 검사 루프, `docs/plans/README.md` 종료 절차, PR.
