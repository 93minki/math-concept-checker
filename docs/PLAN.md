## 목표
진단 화면(F-04, F-06, F-07)이 쓸 **승인된 문제 은행**을 DB에 만든다.
1. 교육과정 데이터(성취기준·개념·평가 항목·오개념·표시 단원)와 문제 은행(문제·보기·채점 요소·백로그) 테이블을 개발 Supabase에 만든다.
2. 고난이도(hard) 문제의 정의를 구체화한 프롬프트 v5를 만든다.
3. 개발자가 실행하는 명령으로 문제를 생성·검증해 DB에 저장하고, 3번 실패한 자리는 백로그에 남긴다.
4. 개발자가 검증 통과 문제를 보고 승인·사용 중지할 수 있다.
5. 성취기준 `9수02-03`으로 실제 문제 은행(평가 항목 6 × 난이도 2 × 변형 3 = 36문제 자리)을 채운다.

이번 계획에 넣지 않는 것: 진단 출제(F-05 "진단 출제" 부분), F-04·F-06·F-07 화면, 진단 기록 테이블(`diagnoses` 등), 나머지 성취기준 59개의 개념 데이터. → 다음 계획.

### 이 작업을 먼저 하는 이유 (근거)
- `docs/PROGRESS.md` "다음 할 일" 후보 4개 중 진단 화면(F-04, F-06, F-07)은 승인된 문제가 있어야 동작한다 (F-05 "학생에게는 승인된 문제만 나간다", `docs/SCORING.md` 3절 "승인된 문제가 없어 제외").
- 고난이도 정의는 문제 은행을 대량으로 만들기 **전에** 고쳐야 한다. 지금 상태로 만들면 hard 문제가 대부분 거절된다 (v4 거절 6건 중 5건, `C4-성질적용` hard는 3번 모두 거절: `docs/plans/2026-11-10_prompt-v3.md` 인계).
- 나머지 59개 개념 데이터는 성취기준마다 사용자 승인이 필요하다 (`docs/DESIGN.md` "개념 데이터 (F-03)" 대표 오개념). 생성·저장 파이프라인을 `9수02-03` 하나로 먼저 검증하면, 이후 개념 데이터가 늘 때 같은 명령으로 채울 수 있다.

## 이전 계획에서 이어받은 것
- 기본 프롬프트는 v4 (`backend/prompts/v4/`). 새 버전은 폴더를 복사해 만들고 이전 버전은 지우지 않는다. v3부터 출력 형식이 바뀌어 v1·v2로는 실행 불가. (출처: plans/2026-11-10_prompt-v3.md, plans/2026-11-10_ai-provider-compare.md)
- 남은 약점: hard 정의가 막연해 검사가 "쉽다"며 거절. (출처: plans/2026-11-10_prompt-v3.md)
- 생성·검증 로직은 `backend/app/ai/tasks.py` `generate_question` (최대 3회 재생성, 코드 검사 → AI 검사), 코드 검사는 `backend/app/ai/validators.py`. 평가 항목 ID·이해 수준은 코드가 채운다. (출처: plans/2026-11-10_prompt-v3.md)
- 실제 AI 호출은 항상 비용 추정과 사용자 승인 후. `--fake`는 AI 호출 없음. (출처: plans/2026-11-10_ai-provider-compare.md)
- 개념 데이터는 문서(`docs/concepts/*.md`)가 기준, `backend/data/concepts/*.json`은 사본. 둘을 함께 고친다. (출처: plans/2026-11-10_ai-provider-compare.md)
- 원격 DB는 개발 프로젝트(`nhbtyedxsjxiybtusnbt`). 원격 적용은 `supabase db push --remote` (미리보기 `--dry-run`), 쓰기는 사용자 승인 후. (출처: plans/2026-11-09_skeleton-login.md, `docs/DESIGN.md` "Supabase CLI")
- 마이그레이션 형식: `supabase/migrations/20261110023848_create_profiles.sql` (RLS 켜기, `revoke all` 후 명시 `grant`, 작업별 정책).
- 위임 지시서에 `.env` 금지, 폴더 밖 변경 금지(TEST_LOG 예외), corepack·전역 설치 금지를 넣는다. pnpm은 `~/Library/pnpm/bin`을 PATH에 직접 넣는다. (출처: plans/2026-11-09_skeleton-login.md)
- Codex 사용 한도 경고가 있었다. 작은 작업은 직접 또는 Cursor로. (출처: plans/2026-11-10_prompt-v3.md)

## 단계
1. **고난이도 정의 초안 → 사용자 승인** — 완료 조건: 이해 수준(정의 이해·성질 적용·오개념 판별·이유 설명)별 hard 조건을 사용자가 승인하고 `docs/DESIGN.md` "문제 데이터와 검증"에 기록.
   - 에이전트가 초안을 쓴다. 출처가 있는 기준을 찾지 못하면 "근거 없음"으로 표시한다 (`AGENTS.md` 3.3).
2. **프롬프트 v5** (`generate_question`, `review_question`에 1단계 정의 반영) — 완료 조건: `9수02-03` hard 6개 항목 실제 생성 시험(비용 추정·승인 후)에서 "쉽다/수준 미달" 거절로 3회 모두 실패해 제외되는 항목 0개. 기본값 `PROMPT_VERSION`을 v5로.
3. **DB 스키마 마이그레이션** (교육과정 5개 + 문제 은행 4개 테이블, `docs/DESIGN.md` "DB 스키마") — 완료 조건: 로컬 검사 통과 후 사용자 승인을 받아 개발 프로젝트에 적용. `authenticated`·`anon`으로 이 테이블들을 읽을 수 없음을 원격에서 확인 (`docs/DESIGN.md` "접근 권한": 학생 접근 불가).
4. **교육과정 데이터 적재 명령** — 완료 조건: 표시 단원 22개와 성취기준 60개 연결이 모두 DB에 들어가고(F-04 완료 조건의 데이터 부분), `9수02-03`의 개념 4·평가 항목 6·오개념 6이 JSON과 같다. 다시 실행해도 중복이 생기지 않는다.
5. **문제 은행 생성 명령** (평가 항목 × 난이도 × 변형 3, 기존 `generate_question` 재사용) — 완료 조건: 통과 문제는 `검증 통과` 상태와 검증 결과·생성 정보(모델, 프롬프트 버전, 시각)·변형 번호와 함께 저장, 3번 실패는 `generation_backlog`에 시도별 실패 이유와 저장. 이미 채워진 자리는 다시 만들지 않는다. 가짜 제공사 테스트로 확인.
6. **개발자 검토·승인 명령** — 완료 조건: `검증 통과` 문제를 HTML로 모아 보고(KaTeX 렌더), 문제를 `승인`(승인자·시각 기록) 또는 `사용 중지`로 바꿀 수 있다. 승인된 문제의 본문·보기·채점 요소는 바꿀 수 없다(DB에서 막음).
7. **`9수02-03` 실제 생성** (비용 추정 → 사용자 승인 → 실행) — 완료 조건: 36자리 중 채워진 수·백로그 수 보고, 사용자가 HTML로 검토해 승인할 문제를 정함.
8. **문서 정리와 계획 종료** — 완료 조건: `docs/DESIGN.md`(hard 정의, 실제 스키마, 명령 사용법), `docs/PROGRESS.md` 갱신, `docs/plans/README.md` 종료 절차.

구현 담당 (`~/.claude/rules/delegation.md`): 1·8과 검수는 Opus, 3~6은 Codex, 단순 수정은 Cursor.

## 1단계 작업: 고난이도 정의 (완료, `docs/DESIGN.md` "고난이도(hard) 정의"로 옮김)

### 지금 거절되는 이유 (v4 실행 `experiments/ai-provider-compare/v4-gen-report-1/calls.jsonl`)
- hard 거절 6건 중 5건이 "쉽다" 판정. 검사가 든 이유는 모두 **계산량·단계 수·오답이 뻔함**이다.
  - "등식의 정리와 간단한 값의 대입만으로 해결" (C2-성질적용), "7을 빼고 2로 나누는 기본적인 두 단계" (C4-성질적용), "②·③은 한쪽에만 연산하고 ⑤는 0으로 나누므로 쉽게 제외" (C4-성질적용)
- 프롬프트 v4의 hard 정의는 한 줄뿐이다: "같은 개념을 더 깊게 묻거나 낯선 상황에 적용하게 하는 문제" (`backend/prompts/v4/generate_question.md:28`). 검사 프롬프트에는 hard 기준이 없다.
- 그런데 범위 조건은 "문자 하나 일차식까지"로 계산을 어렵게 만들 여지를 막는다. 생성기는 범위를 지키고, 검사는 계산량으로 판단해 서로 엇갈린다. (에이전트 분석)

### 근거로 쓸 교육과정 원문 (`docs/[별책8] 수학과 교육과정.pdf`)
- 중학교 "변화와 관계" 고려 사항: "방정식, 부등식, 함수에 대한 **지나치게 복잡한 활용 문제는 다루지 않는다**." (37쪽)
  - → 고난이도를 계산량이나 복잡한 활용으로 만들면 안 된다.
- 평가 방법 (나) 교과 역량 평가 (48쪽):
  - 추론: 개념·원리를 이해하는지, 추측의 근거를 제시하는지, **타당한 정당화**를 하는지, 근거를 바탕으로 비판적으로 사고하는지
  - 의사소통: **수학적 표현 간에 변환**을 할 수 있는지
  - 연결: 개념·원리를 적절하게 관련지어 이해하는지, 실생활에 적용할 수 있는지
- 공식 성취수준(상·중·하) 문구는 찾지 못했다 (웹 검색, 2026-11-10). → 아래 이해 수준별 조건은 **에이전트 제안(근거 없음)**이다. 위 원문은 방향만 뒷받침한다.

### 제안 정의
**공통 원칙**
- 고난이도는 같은 평가 항목(개념 × 이해 수준)과 같은 범위 조건 안에서 **생각할 거리**를 늘린 문제다. 계산 단계 수, 수의 크기, 식의 길이를 늘려 어렵게 만들지 않는다 (원문 "지나치게 복잡한 활용 문제는 다루지 않는다").
- 일반 문제: 전형적인 예, 한 가지 표현(식), 정의·성질을 바로 확인하면 풀린다.
- 고난이도: 아래 이해 수준별 조건 중 **하나 이상**을 만족한다. 문제 생성 시 어느 조건을 썼는지 출력하게 하고, 검사는 그 조건을 실제로 만족하는지로 판정한다.

| 이해 수준 | 고난이도 조건 (하나 이상) | 원문 방향 |
|---|---|---|
| 정의 이해 | (a) 정의의 조건을 하나하나 따져야 판단되는 **경계 사례** (예: 참이 아닌 등식, 문자가 없는 등식, 양변이 같은 식) (b) 일상 언어·표로 주어진 것을 식으로 바꿔 판단 | 추론(개념 이해), 의사소통(표현 변환) |
| 성질 적용 | (a) **거꾸로** 쓰기 (결과가 주어지고 조건을 찾기, 예: 해가 주어졌을 때 계수 구하기) (b) 문장·상황으로 주어져 식으로 바꾼 뒤 적용 (c) 여러 단계 중 **어느 단계에서** 어떤 성질이 쓰였는지·틀렸는지 판단 | 연결, 의사소통, 추론 |
| 오개념 판별 | (a) 오답 보기가 **모두** 승인된 오개념 또는 그럴듯한 부분 참에서 나옴 (b) 다른 학생의 주장·풀이를 보고 옳고 그름을 판단 | 추론(비판적 사고) |
| 이유 설명 | (a) 특정 수가 아니라 **모든 경우**에 성립하는 이유 설명 (b) **반례**를 들어 주장이 틀렸음을 보이기 (c) 두 풀이 방법이 같은 결과를 내는 이유 비교 | 추론(정당화·일반화) |

**검사 기준 (review 프롬프트에 추가)**
- 계산이 짧거나 수가 작다는 이유만으로 hard를 거절하지 않는다.
