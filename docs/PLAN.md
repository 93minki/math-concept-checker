## 목표
1. **다크모드 그림 결함을 먼저 고친다.** 다크모드에서 수직선의 ●/○가 뒤집혀 보이고 선이 거의 안 보인다. 고치는 방식은 결정 1: 모든 문제를 흰 배경·검은 글씨 판에 보인다.
2. 성취기준 58개의 평가 항목 276개마다 **그림을 넣을지 에이전트가 근거와 함께 제안**하고 사용자 승인을 받는다.
3. 승인 결과에 필요한 **새 그림 종류(도형 포함)** 를 설계·구현한다.
4. 승인된 그림 평가 항목을 개념 데이터에 반영하고, 비용 상한 안에서 문제를 생성·검토·승인한다.

이번 계획에 넣지 않는 것
- 학생이 직접 그리는 입력 (지난 계획 결정 3 유지: "그리기"는 그림 보기 고르기).
- 남은 중3 (`9수02-21`, `9수03-18`, `9수02-22`·`9수03-19`의 고난이도와 변형 2). 이 계획 다음에 한다 (PROGRESS "다음 할 일").
- 해설 안 그림, 그림 위 글의 KaTeX (지난 계획 결정 4, `docs/DESIGN.md` "그림 데이터").
- 고난이도 정의 재검토, 빈자리 채우기, Docker 배포, F-02, F-11.

### 이 작업을 하는 이유 (근거)
- 사용자 결정 (2026-11-12): 다음 계획은 그림 그리기 확장. 기준은 "그림이 이해에 조금이라도 도움이 되면 넣는다" (`docs/DESIGN.md` "그림을 넣는 기준", `docs/plans/2026-11-12_figures.md` 진행 메모).
- 다크모드 결함: 그림 선은 `#222`, ○ 안은 `white`로 고정이고 SVG에 배경이 없다 (`frontend/src/lib/figures/index.ts:93`, `:115-123`). 다크모드 배경은 `#0a0a0a`다 (`frontend/src/app/globals.css:6-11`). 그래서 ●(`#222`)는 배경에 묻혀 빈 원처럼, ○(흰 채움)는 꽉 찬 원처럼 보인다. 부등식의 해에서 ●/○는 "포함/불포함"이라 답이 뒤바뀐다 (`9수02-12-C4`).
- 지금 그림 평가 항목은 시험 3개뿐이다 (276개 중, `backend/data/concepts/*.json` 집계 2026-11-12). 도형 성취기준(`9수03-xx`, 평가 항목 81개)은 그림 종류가 없어 모두 글로만 묻는다 (`docs/DESIGN.md` "그림 없는 문제").

## 이전 계획에서 이어받은 것
- 그림은 AI가 **데이터(JSON)** 만 만들고 우리 코드가 SVG로 그린다. 코드가 수치를 검사한다. AI 글을 HTML로 넣지 않는다. (출처: plans/2026-11-12_figures.md 결정 1, `docs/DESIGN.md` "그림")
- 그리기 코드는 `frontend/src/lib/figures/`(프레임워크 없는 TS) 하나를 학생 화면과 `review-html`이 같이 쓴다. (출처: `docs/DESIGN.md` "화면 (F-06)")
- 그림 평가 항목 생성 실패는 모두 개념 데이터 문구 때문이었다: 범위 문장의 "그림 없음" 문구 잔존, 만들 수 없는 보기 구성, 보기별 오개념 미지정, 여러 요소를 모두 담으라고 읽힘. `docs/DESIGN.md` "개념 데이터 작성 규칙"을 처음부터 따른다. (출처: plans/2026-11-12_figures.md 인계)
- 그림 문제 검토는 실제 그림을 학생 화면 크기(본문 약 330px, 보기 약 250px)로 그려 스크린샷으로 본다. 그리기 결함 3종은 이렇게 해서만 찾았다. (출처: `docs/DESIGN.md` "시험 결과")
- 개념 문서 → JSON은 `uv run python -m app.bank convert-concepts`, 표 칸 안의 `|`는 `\|`. (출처: `docs/DESIGN.md` "개념 데이터 (F-03)")
- 생성 전 최소 호출로 API 키 확인, 동시 생성 3~4개, 에이전트가 모든 문제의 정답·오개념 연결·범위를 확인 후 `master`로 승인, 짚은 문제만 사용자에게. (출처: plans/2026-11-12_grade3-part1.md, `docs/DESIGN.md` "문제 은행")
- Codex 샌드박스는 E2E를 못 돌린다. E2E는 Opus가 직접 돌린다. 임시 파일은 `.agent-tasks/`, `experiments/scratch/`, `frontend/test-results/`. (출처: plans/2026-11-12_figures.md 인계)
- 남은 크레딧 약 $12.6 (PROGRESS 2026-11-12, 에이전트 계산). 문제당 실측 약 $0.018 (중3 1차 $4.02 ÷ 218), 그림 시험은 재생성 포함 문제당 약 $0.097 ($0.967 ÷ 10).

## 결정 사항 (사용자 결정, 2026-11-12)
사용자 원문: "1. 모든 문제는 흰색 배경에 검은색 글씨가 나왔으면 좋겠어 이건 다크모드 뿐만아니라 라이트모드도 같이 고려해야 한다. 라이트모드에서 배경색이 하얀색이라면 구분이 안갈테니까 2. 기존 문제 사용 중지해도 상관 없고 필요한 문제들은 그림 항목으로 바꿔 3. 범위 전체 보고 나머지는 추천대로 진행해라 구현해도 된다"
- 결정 1은 아래 추천안 대신 **사용자 안**: 문제(본문·표·그림·보기)를 **흰 배경, 검은 글씨 판**에 보인다. 라이트·다크 모두 같다. 라이트모드는 페이지 배경도 흰색이라 판이 구별되도록 테두리 등으로 경계를 준다 (구체 모양은 단계 1 스크린샷으로 확인).
- 결정 2는 안 A (기존 항목을 그림 항목으로 바꾸고 기존 문제 사용 중지, 사용자 "사용 중지해도 상관 없다"). 결정 3은 276개 전체. 결정 4~6은 추천안.
- 구현 허락 (`AGENTS.md` 3.1): 이 계획의 단계 1·4와 단계 6의 생성 실행(상한 $5)에 적용한다.

아래는 초안 때 적은 선택지다.


1. **다크모드 고치는 방식**
   - 추천 (안 A): 그림에 **흰 배경 판**을 깐다 (SVG 첫 요소로 흰 사각형, 둥근 모서리). 선·글자 색은 지금대로 둔다.
     - 근거: 그리기 코드가 색을 고정 값으로 넣으므로 배경만 정하면 어느 테마에서도 같은 그림이 된다. `review-html`(따로 실행하는 SVG)에도 CSS 없이 그대로 맞는다 (`docs/DESIGN.md` "화면 (F-06)").
   - 다른 안 B: 선·채움을 CSS 변수(`currentColor`, 배경색 변수)로 바꿔 다크모드에서 흰 선으로 그린다. 화면과 어울리지만 ○ 채움을 배경색에 맞춰야 하고 `review-html`에 같은 CSS를 넣어야 한다.
   - 테스트: Vitest(흰 배경 요소가 있음), Playwright를 다크모드(`colorScheme: 'dark'`)로도 한 번 실행해 그림 스크린샷 확인.
2. **기존 평가 항목에 그림을 넣는 방식**
   - 추천 (안 A): **기존 평가 항목을 그림 항목으로 바꾼다** (`figure`를 `none` → `body`/`choices`). 새 그림 문제를 승인한 자리부터 같은 자리의 기존 글 문제를 사용 중지한다.
     - 근거: 평가 항목 = (개념, 이해 수준)이고 항목 × 난이도마다 문제 하나라서 (`docs/features.md` F-05), 항목을 늘리면 진단 문제 수가 늘어난다. 바꾸면 진단 길이가 그대로다. 승인 문제는 고치지 않으므로 사용 중지 후 새 문제로 바꾸는 것이 정해진 방법이다 (`docs/DESIGN.md` "문제 상태").
     - 생성 전 사용 중지가 필요하다 (한 자리에 살아 있는 문제 하나). 개발 프로젝트라 학생 영향은 없다. 그림 생성이 백로그로 끝난 자리는 기존 문제를 다시 쓸 수 없으므로(사용 중지 되돌리기 없음) **사용 중지 전 새 문제를 먼저 만들 방법**을 단계 3에서 정한다 (예: 생성 결과를 저장하지 않고 검토 후 교체).
   - 다른 안 B: 그림 평가 항목을 새로 더한다. 기존 문제가 그대로 남지만 진단 문제 수가 늘고, 같은 개념·수준을 두 번 잰다.
3. **그림 여부 제안 범위와 승인 단위**
   - 추천: 276개 항목 전체를 본다. 성취기준마다 표 하나(항목, 그림 여부 `none`/`body`/`choices`, 그림 종류, 근거)로 만들어 **영역별 4묶음**(수와 연산, 변화와 관계, 도형과 측정, 자료와 가능성)으로 승인받는다.
   - 근거 칸에는 `docs/DESIGN.md` "그림을 넣는 기준"대로 교육과정 원문(쪽), 교과서가 그림으로 다루는지(확인 못 하면 "근거 없음"), 그림이 있을 때와 없을 때의 차이를 적는다.
4. **새 그림 종류 (후보, 결정 3 승인 결과로 확정)**
   - `geometry` 평면도형: 점(이름, 좌표), 선분(같은 길이 표시, 길이 글, 점선), 직선·반직선, 다각형, 원·호, 각 표시(크기 글, 직각 표시, 같은 각 표시). 대상 예: 맞꼭지각·동위각·엇각(`9수03-01·02`), 작도 결과, 삼각형·사각형 성질, 외심·내심, 닮음, 피타고라스, 삼각비, 원주각, 부채꼴.
     - 코드 검사 (상한·허용 오차는 에이전트 추정, 근거 없음): 참조한 점이 있음, 좌표가 창 안, 점 ≤ 12, 직각 표시는 실제 90°, 같은 길이·같은 각 표시는 실제로 같음, 각 크기 글과 그려진 각의 차이가 일정 범위 안, "원 위의 점"은 실제로 원 위.
   - `solid` 입체도형: 정해진 모양(직육면체, 각기둥, 각뿔, 원기둥, 원뿔, 구, 각뿔대·원뿔대) + 치수 글 + 꼭짓점 이름, 보이지 않는 모서리는 점선. AI는 모양과 치수만 정한다. 대상: `9수03-07·08`.
   - 전개도: 정육면체·직육면체·원기둥·원뿔 전개도를 정해진 모양으로 (`9수03-07`). 정육면체 전개도는 접히는 배치인지 코드가 검사한다.
   - 기존 종류 확장: 좌표평면에 꺾은선 그래프(시간-거리, `9수02-06`)·반비례 곡선(`9수02-07`)·축 이름, 막대그래프 세로축 시작값(`9수04-04` 잘못 그린 그래프), 도수분포다각형의 상대도수(`9수04-03`), 수직선 점 이름에 `√`(`9수01-09`).
   - 결정 3 결과에 쓰이지 않는 종류는 만들지 않는다.
5. **생성 비용 상한과 우선순위**
   - 추천: 이 계획 생성 상한 **$5** (남은 약 $12.6 중. 남은 중3 생성에 쓸 몫을 남긴다).
   - 순서: (1) 새 그림 종류마다 시험 항목 1개씩 먼저 생성해 그리기 결함을 찾는다 (지난 계획과 같은 방식). (2) 그 뒤 PROGRESS "그림 지원 필요" 목록 항목. (3) 나머지 승인 항목.

6. **작업 분담** (`~/.claude/rules/delegation.md`): 설계·그림 여부 제안·개념 데이터·지시서·검수·E2E·그림 스크린샷 검토는 Opus, 구현(그리기 코드, 백엔드 스키마·코드 검사, 프롬프트 그림 절 반영, 테스트)은 Codex. **코드 작성은 `AGENTS.md` 3.1에 따라 사용자 허락이 필요하다.**
