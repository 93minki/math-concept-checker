## 목표
1. 한 계정은 하루에 개념 체크 **3번**까지만 AI 채점을 받을 수 있다. 1번 = 진단 하나의 1단계 제출(AI 채점이 처음 실행되는 때). 서버가 막는다.
2. 지정한 계정은 횟수 제한을 받지 않는다.
3. 학생은 오늘 남은 횟수를 보고, 다 쓰면 왜 제출할 수 없는지 안다.
4. 2단계에서 학생이 "여기까지 하고 리포트 보기"로 직접 끝내고 바로 리포트를 본다(1단계 제출로 1번을 썼으므로 리포트를 기다리지 않게).

이번 계획에 넣지 않는 것
- 진단 하나 안의 AI 호출 수 제한: 진단 한 번에 AI 호출은 최대 3번(1단계 채점·2단계 채점·리포트)으로 이미 정해져 있다(`PROGRESS.md` "사용자별 AI 호출 제한").
- 관리자 AI 수정안(F-13)의 횟수 제한: 관리자만 쓰는 기능이다.
- 계정을 여러 개 만드는 경우: 이메일 확인 없이 가입되므로(사용자 결정 2026-11-15) 새 계정을 만들면 3번을 다시 쓸 수 있다. 이번 제한은 "한 계정당"까지만 막는다.

### 이 작업을 하는 이유 (근거)
- 사용자 2026-11-15: "사용자별 AI 호출 제한만 추가하자. 하루에 한 아이디당 개념 체크를 3개만 할 수 있도록. (단, 특정 아이디는 제한 없게 할 수 있어야 함.)"
- `PROGRESS.md` "실제 학생 공개 전 필수 항목": 사용자별 AI 호출 제한은 공개 전에 정한다(사용자 결정 2026-11-10).

## 이전 계획에서 이어받은 것
- 관리자 표시는 별도 테이블 `admins`(RLS 켬, 정책 없음, 서버가 Secret key로만 읽음, 첫 행은 사용자가 직접 넣음)로 했다(사용자 결정). 제한 제외 계정도 같은 방식으로 만든다. (출처: plans/2026-11-15_question-reports.md, `DESIGN.md` "문항 오류 신고와 관리")
- 배포 서버는 개발 Supabase 프로젝트와 실제 AI를 쓴다. 반영은 서버 맥북에서 `git pull` 뒤 `docker compose ... up -d --build`(사용자). (출처: plans/2026-11-15_docker.md 인계)
- 위임 환경(Codex)은 포트·Chromium·Docker가 막혀 있어 E2E는 Opus가 돌린다. 시험 계정 A·B는 절대 바꾸지 않는다. `test:e2e:dev`는 3100·8100 임시 복사본. 사용자 서버 3000·8000은 끄지 않는다. (출처: plans/2026-11-15_docker.md, 2026-11-15_question-reports.md 인계)
- 2026-11-15 사용자 결정으로 F-11 삭제·이메일 확인 끔(문서는 이미 고쳤고 아직 커밋 전). 남은 코드 주석 `frontend/src/app/signup/complete/complete-signup.tsx:30`("F-11 단계가 여기 들어간다")을 지우는 제안이 승인됐다. 이 문서 변경과 주석 정리를 이 계획 브랜치에 함께 올린다.

## 결정 (에이전트 추천, 사용자 확인 필요)
1. **무엇을 1번으로 세나: 진단 하나의 1단계 제출 = 1번** (사용자 결정 2026-11-15 "실제 AI 채점 실행 횟수로 처리하자").
   - 진단 한 번의 AI 호출은 1단계 채점 → (통과 항목이 있으면) 2단계 채점 → 리포트 순서다(`DESIGN.md` 진단 API, `backend/app/diagnoses/service.py:110`·`:335`). 그중 **첫 AI 채점인 1단계 제출에서 1번을 센다.**
   - 같은 진단의 2단계 제출과 리포트 만들기는 세지 않고, 3번을 다 쓴 뒤에도 막지 않는다. 막으면 1단계까지 채점한 진단이 리포트 없이 끝난다.
   - 그래서 기본 문제(1단계)만 풀고 제출해도 1번이다. 2단계까지 가도 1번이다. 2단계 도중 그만둔 진단도 1번이다(1단계 제출 때 이미 셈).
   - 세지 않는 것: 진단 시작, 답 저장, "새로 시작하기"로 1단계 제출 전에 버린 진단, AI 채점이 실패한 제출(503 `grading_failed` — 아무것도 기록되지 않는다, `DESIGN.md` 결정 2026-11-10).
   - 막는 때: 1단계 제출 요청에서 **AI를 부르기 전에** 센다. 이미 3번이면 AI를 부르지 않고 429 `daily_limit`. 같은 사람이 여러 탭에서 동시에 제출해 넘치는 것은 DB 제출 함수(`diagnosis_submit_stage1`) 안에서 사용자별 잠금으로 다시 확인해 기록이 3번을 넘지 않게 한다(이 경우 AI 1번은 이미 쓴 뒤라 버려질 수 있다).
   - 진단 시작과 답 쓰기는 막지 않는다. 진행 중 진단은 단원마다 하나씩 둘 수 있어서(`DESIGN.md` 진단 시작 규칙 2), 여러 단원을 풀어 둘 수 있다. 다 쓴 날 제출하면 막히고, 답은 저장된 채로 남아 다음 날(3일 자동 중단 전) 제출할 수 있다.
2. **하루의 기준: 한국 시간 0시.** 1단계 제출 시각(`diagnoses.stage1_submitted_at`)이 오늘 0시(Asia/Seoul) 이후인 내 진단 수를 센다. 새 저장 공간이 필요 없다. 어제 시작해 오늘 제출하면 오늘 1번이다.
3. **제한 없는 계정: 새 테이블 `diagnosis_limit_exempt`(`user_id`, 지정 시각, 메모).** RLS 켬·정책 없음(학생은 읽지도 쓰지도 못함), 탈퇴 시 함께 삭제. 넣고 빼기는 사용자가 Supabase SQL 편집기에서 한다(관리 화면은 만들지 않음).
   - 관리자(`admins`)를 자동으로 제외하지는 않는다. 관리자 계정도 제외하려면 이 테이블에 넣는다. (두 권한을 따로 다룰 수 있게)
4. **횟수 3은 백엔드 환경 변수 `DAILY_DIAGNOSIS_LIMIT`(기본 3).** 바꾸려면 서버 맥북 `backend/.env`에 넣고 다시 띄운다.
5. **시험 계정 A·B를 제외 목록에 넣는다(사용자가 SQL로).** `test:e2e:dev`가 진단을 시작하므로, 넣지 않으면 하루 세 번째 실행부터 E2E가 실패한다. 계정 자체는 바꾸지 않고 제외 테이블에 행만 더한다.
6. **화면**
   - 학습 지도 위쪽(진도 요약 띠)에 "오늘 남은 개념 체크 2/3". 제한 없는 계정에는 보이지 않는다.
   - 다 쓴 날 단원을 시작하려 하면 시작 전에 알린다: "오늘 채점 3번을 모두 썼어요. 지금 풀어 두면 내일 0시부터 제출할 수 있어요." 시작은 막지 않는다.
   - 1단계 제출 확인 모달에 "제출하면 오늘 남은 채점이 1번 줄어요 (남은 횟수 2)"를 보인다. 다 썼으면 제출 버튼을 끄고 위 문장을 보인다.
   - 서버가 막은 경우(다른 탭에서 제출 등)도 같은 문장을 보이고, 답은 그대로 남는다.

7. **2단계 "여기까지 하고 리포트 보기"** (사용자 결정 2026-11-15 "너 제안대로 가자")
   - 2단계 화면의 버튼 → 확인 창 "남은 심화 문제는 풀지 않은 것으로 처리돼요" → 진단을 중단(`abort_reason` 새 값 `stopped`, 학생이 직접 끝냄)으로 바꾸고 리포트로 간다.
   - 리포트는 기존 "2단계 도중 중단" 규칙 그대로(1단계 결과 + 2단계에서 답한 문제, 미응답 0.5 `deep_not_attempted`, `SCORING.md`). 리포트 AI는 횟수에 세지 않는다.
   - 지난 기록에는 지금처럼 "중단"으로 보이고 리포트를 열 수 있다.
   - 새 요청 `POST /diagnoses/{id}/stages/2/stop`: 404(없거나 남의 진단), 409(2단계 진행 중이 아님). 답한 2단계 답안은 채점에 들어간다.
- 다 쓴 날 진단 시작은 막지 않고 안내만 한다(결정 6, 사용자 승인 2026-11-15).

## 단계
1. **문서·설계** — `features.md`에 F-14 추가(목적·동작·완료 조건), F-06에 "2단계에서 직접 끝내면 2단계 도중 중단과 같이 리포트", `DESIGN.md`에 테이블·API·화면 설계, `PROGRESS.md`. GitHub 라벨 `F-14` 만들기. 완료 조건: 사용자 확인.
2. **DB** — 마이그레이션: `diagnosis_limit_exempt` 테이블, `diagnosis_submit_stage1`에 사용자별 잠금과 횟수 재확인(제외 계정·한도는 인자로), `abort_reason`에 `stopped` 추가와 2단계 직접 끝내기 함수. 로컬 Postgres 컨테이너에서 학생 역할이 읽기·쓰기 거부되는지 시험. 개발 프로젝트 적용은 사용자(`supabase db push`), 그 뒤 사용자가 SQL로 시험 계정 A·B와 원하는 계정을 넣는다. 완료 조건: 원격 권한 조회로 학생 역할 접근 없음 확인.
3. **백엔드** — `POST /diagnoses/{id}/stages/1/submit`에서 제외 계정이 아니면 AI를 부르기 전에 오늘(한국 시간) 1단계 제출 수를 세어 3 이상이면 **429 `daily_limit`**(`{limit, used, resets_at}`). DB 제출 함수에서 사용자별 잠금으로 다시 확인(마이그레이션은 2단계에 포함). 남은 횟수 조회 `GET /diagnoses/quota` → `{limit, used, remaining, unlimited, resets_at}`. 테스트: 3번째 제출까지 성공·4번째 429이고 AI(가짜)가 불리지 않음, 2단계 제출·리포트는 다 쓴 뒤에도 됨, AI 실패 제출은 안 셈, 진단 시작은 안 막음, 0시 경계, 제외 계정 무제한, 로그인 없으면 401, 다른 사용자의 기록은 세지 않음. `stages/2/stop`: 끝낸 뒤 리포트 생성(가짜 AI)·답한 2단계 문제 반영, 1단계·완료·남의 진단은 거부. 완료 조건: 백엔드 5.2 통과.
4. **프론트** — 학습 지도 남은 횟수 표시, 다 쓴 날 시작 전 안내, 제출 확인 모달의 남은 횟수·제출 끔, 429 처리, 2단계 "여기까지 하고 리포트 보기" 버튼·확인 창, `complete-signup.tsx:30` 주석 정리. 테스트: Vitest(표시·버튼 끔·429 문장), Playwright 360px 넘침 없음. 완료 조건: 프론트 5.2 통과.
5. **검수·종료** — 5.2 전체, `test:e2e:dev`(시험 계정 A·B 제외 등록 뒤), 데스크톱·폰 확인(사용자: 제외하지 않은 계정으로 배포 주소에서 4번째 1단계 제출이 막히는지), 계획 종료, PR. 배포 반영은 사용자가 서버 맥북에서.
