## 목표

로그인한 학생이 **표시 단원을 골라 1단계(일반 문제) 진단을 시작하고, 문제를 풀고, 제출**할 수 있게 한다. 진단과 답안은 계정에 저장되어 이탈해도 이어서 풀 수 있다.

1. 진단 기록 테이블(`diagnoses`, `diagnosis_items`, `answers`)을 만든다. 학생은 자기 기록만 읽고, 쓰기는 백엔드만 한다.
2. 단원 선택 화면 (F-04): 표시 단원 23개, 학년·기준 출판사 표시, 별칭 검색, 진행 중인 진단 표시.
3. 진단 출제 (F-05): 1단계는 단원의 모든 평가 항목에 승인된 일반 문제를 하나씩 고른다. 아직 보지 않은 변형을 우선한다. AI를 부르지 않는다.
4. 풀이 화면 (F-06): 객관식 선택, 서술형 일반 텍스트 입력, 답할 때마다 서버 저장, 이어 풀기, 새로 시작 확인, 3일 후 자동 중단, 1단계 제출.

이번 계획에 넣지 않는 것 → 다음 계획

- F-07 채점 (객관식 정답 비교, 서술형 AI 채점, 이해도 계산), 2단계(고난이도) 출제, `gradings`·`reports` 테이블
- F-08 리포트, F-10 지난 기록 목록
- 프롬프트의 "필수:" 형식 수정 (채점 프롬프트라 F-07 계획에서)
- 나머지 성취기준 59개 개념 데이터 (F-03), Docker 배포

1단계 제출이 끝나면 화면에 "제출했어요. 채점 기능은 준비 중이에요" 같은 안내만 보인다. 채점으로 넘어가는 것(F-06 마지막 완료 조건)은 다음 계획에서 잇는다.

### 이 작업을 먼저 하는 이유 (근거)

- `docs/PROGRESS.md` "다음 할 일"의 갈림길은 "진단 흐름 먼저"와 "개념 데이터 먼저" 중 하나다.
- 진단 흐름을 먼저 하는 이유
  - 학생 기능(F-04 ~ F-10)이 하나도 없다. 마일스톤 `M2 문제 은행·진단`에서 남은 것이 F-04, F-06, F-07, F-09다 (GitHub 마일스톤 설명).
  - 지금 데이터로 흐름 전체를 돌릴 수 있다: `9수02-03` 승인 문제 36개, 표시 단원 23개, 성취기준 60개 연결이 개발 DB에 있다 (2026-11-10 이 PC에서 읽기 전용 조회로 확인).
  - 문제 은행 계획은 "파이프라인을 성취기준 하나로 먼저 검증하고, 개념 데이터가 늘면 같은 명령으로 채운다"는 전제로 진행했다 (`docs/plans/2026-11-10_question-bank.md` "이 작업을 먼저 하는 이유").
- 개념 데이터를 나중에 하는 이유

  - 데이터만 늘려서는 학생이 쓸 수 있는 기능이 생기지 않는다.
- 이 계획에서 채점을 빼고 1단계 제출까지만 하는 이유: 근거 없음 (에이전트 판단). 이전 계획들은 단계가 8개 안팎이었고, 진단 테이블·API·화면 2개·E2E만으로 그만큼이 된다. 사용자도 채점·2단계·리포트를 다음 계획으로 정했다 (결정 7).

## 이전 계획에서 이어받은 것

- 진단 출제는 `questions`에서 `status = 'approved'`만 쓴다. 학생은 문제 은행 표를 직접 읽을 수 없으므로 백엔드가 정답을 뺀 문제를 내려 준다. (출처: plans/2026-11-10_question-bank.md 인계)
- 표시 단원은 23개다 ("22개"는 오기). (출처: plans/2026-11-10_question-bank.md 인계)
- 마이그레이션 절차 (출처: plans/2026-11-10_question-bank.md 인계)
  - 버리는 Postgres 17 컨테이너(`postgres:17`)에 역할(anon, authenticated, service_role)을 만들고 먼저 시험한다. 끝나면 컨테이너를 지운다 (`AGENTS.md` 3.9).
  - 원격 적용(`supabase db push --remote --yes`)은 Claude Code 자동 모드가 막으므로 사용자가 다른 터미널에서 직접 실행한다.
  - 원격 읽기 전용 조회(`supabase db query --remote --read-only`)는 에이전트가 실행할 수 있다.
- 마이그레이션 형식: RLS 켜기, `revoke all` 후 명시 `grant`, 작업별 정책, `(select auth.uid()) = user_id`, `user_id` 인덱스. (출처: `supabase/migrations/20261110023848_create_profiles.sql`, `docs/DESIGN.md` "접근 권한 (RLS)")
- 여러 표를 한 번에 쓰는 일은 DB 함수 하나로 한 트랜잭션에 처리한다 (예: `bank_insert_question`, `service_role`만 실행). (출처: `docs/DESIGN.md` "문제 은행 (F-05)")
- 서버 코드는 `getClaims()`로 로그인을 확인하고 `getSession()`을 믿지 않는다. 보호 규칙은 `src/proxy.ts`와 `(protected)/layout.tsx` 두 겹이다. (출처: plans/2026-11-09_skeleton-login.md, `docs/DESIGN.md` "인증 (F-01)")
- 프론트 E2E는 가짜 공개 env와 secret canary로 돈다. 실제 `.env.local`은 필요 없다. (출처: plans/2026-11-09_skeleton-login.md 인계)
- pnpm은 `~/Library/pnpm/bin`을 PATH에 직접 넣는다. corepack은 쓰지 않는다. (출처: plans/2026-11-09_skeleton-login.md 인계. 2026-11-10 집 PC에서도 corepack 설치가 멈춤)
- pnpm 12 공급망 정책에 걸리면 예외를 추가하지 말고 하루 지난 버전으로 고정한다. (출처: plans/2026-11-09_skeleton-login.md 인계)
- 수식 렌더링: 문제 본문의 수식은 KaTeX `$...$`. 별도 줄 수식에는 줄바꿈 CSS를 쓰고, `\overparen`은 쓰지 않는다. (출처: `docs/DESIGN.md` "수식 렌더링", "문제 하나에 담는 정보")
- 원격 시험 계정은 확인 후 지운다. (출처: plans/2026-11-09_skeleton-login.md 인계) → 이번 계획에서 바꿈: 시험 계정 A·B를 남겨 계속 쓴다 (결정 8).
- 위임 지시서에 다음을 넣는다. (출처: plans/2026-11-09_skeleton-login.md, plans/2026-11-10_question-bank.md 인계)
  - `.env` 금지, 폴더 밖 변경 금지(TEST_LOG 예외), corepack·전역 설치 금지
  - 구현 허락 문구를 사용자 원문으로 인용
  - 프로세스 정리 (`AGENTS.md` 3.9)
- 위임 결과는 검수에서 실제 동작을 확인한다. 지난 계획에서 잡은 위임 실수: `# noqa` 추가, 테스트 기대값 맞춤 수정. Codex는 샌드박스에서 포트를 열지 못해 E2E를 못 돌린다. (출처: plans/2026-11-10_question-bank.md 인계)

## 결정 사항 (사용자 결정, 2026-11-10)

초안의 "결정이 필요한 것" 9개에 대한 사용자 답이다. 1단계에서 `docs/DESIGN.md`에 옮긴다.

1. **문제가 없는 단원의 표시**: 23개를 모두 보여 주고, 승인 문제가 없는 단원은 "준비 중"으로 표시해 시작할 수 없게 한다. (F-04 완료 조건이 23개 단원과 60개 성취기준 연결을 요구한다)
2. **일부만 준비된 단원**: 시작을 허용하고 "이 단원은 일부 내용만 진단해요"를 안내한다.
   - 대상: "중1 3 문자의 사용과 식". 성취기준 4개 중 `9수02-03`만 개념 데이터가 있다.
   - 나머지 3개(9수02-01, 02, 04)는 평가 항목 자체가 없다. `docs/SCORING.md`의 "측정 안 함"(평가 항목은 있으나 문제가 없음)과 다른 경우다.
3. **3일 자동 중단**: 백엔드가 그 학생의 진단을 읽거나 쓸 때마다, 시작 후 3일이 지난 "진행 중" 진단을 먼저 "중단(기간 만료)"으로 바꾼다. 예약 작업(Supabase `pg_cron`)은 나중에 고려한다.
4. **출제 순서와 변형 고르기**
   - 문제 순서는 개념 순(C1→C4) 안에서 이해 수준 순으로 고정한다.
   - 보기 순서는 저장된 순서 그대로 둔다.
   - 보지 않은 변형이 여럿이면 그중 무작위로 고른다.
5. **서술형 답안 길이 제한**: 1,000자.
6. **풀이 화면 구성**: 한 화면에 한 문제를 보인다.
   - 이전·다음 버튼과 진행 표시(예: 3/6)를 둔다.
   - 모든 문제에 답해야 제출 버튼이 켜진다 (F-06 "그 단계의 모든 문제를 푼 뒤 제출").
7. **범위**: 이 계획은 1단계 제출에서 끝낸다. 채점(F-07), 2단계 출제, 리포트(F-08)는 다음 계획에서 한다.
8. **로그인이 필요한 화면의 테스트**: 로컬 Supabase는 쓰지 않는다. 개발·테스트용 Supabase 프로젝트에 시험 계정을 두고 시험한다.
   - 이 구성은 이미 기록되어 있다: `docs/DESIGN.md` "실행 환경 분리 (사용자 결정, 2026-11-10)". 지금 프로젝트(`nhbtyedxsjxiybtusnbt`)가 개발·테스트용이고, 운영용은 배포 직전에 새로 만든다.
   - 시험 계정 2개(A, B)는 지우지 않고 계속 쓴다. 이전 계획의 "시험 계정은 확인 후 지운다"를 바꾼다.
     - 2개인 이유: 계정 A로 계정 B의 진단·답안을 읽거나 쓸 수 없는지 확인해야 한다 (`AGENTS.md` 3.7-5, F-09 완료 조건)
     - 방식: 이메일 + 비밀번호. 카카오 로그인은 자동 테스트로 통과시킬 수 없어 쓰지 않는다 (F-01에서 사용자가 직접 확인함: plans/2026-11-09_skeleton-login.md)
     - 사용자가 만들고 비밀번호를 환경 변수 파일에 넣는다. 에이전트는 그 파일을 읽지 않는다 (`AGENTS.md` 4.3). 테스트 프로그램이 실행 중에 읽는다.
   - 원격 접속 범위 (사용자 결정, 2026-11-10): **로그인 흐름 확인에만** 원격 Supabase 접속을 허용한다. 1단계에서 `AGENTS.md` 5.4에 이 예외를 적는다.
     - 기존 `pnpm test:e2e`(5.2의 5번)와 백엔드·Vitest 테스트는 지금처럼 원격 호출이 없다.
     - 로그인 흐름 E2E는 개발 프로젝트를 쓰는 별도 명령으로 만들고, 화면을 바꾼 단계와 계획 종료 때 실행한다.
   - 시험 계정 환경 변수 (2026-11-10 정함): 파일 `frontend/.env.e2e` (git 제외), 이름 `E2E_USER_A_EMAIL`, `E2E_USER_A_PASSWORD`, `E2E_USER_B_EMAIL`, `E2E_USER_B_PASSWORD`. 자리표시는 `.env.sample`.
     - 별도 파일인 이유: Next.js는 `.env.local`과 `.env.<NODE_ENV>`를 앱에 읽어 들인다. `.env.e2e`는 읽지 않으므로 시험 비밀번호가 앱이나 빌드에 들어가지 않는다 ([Next.js Environment Variables](https://nextjs.org/docs/app/guides/environment-variables)).
   - 1단계에서 정할 것: 시험 계정의 진단 기록을 테스트 전후에 정리하는 방법, 별도 명령 이름

9. **구현 담당**: 회사 PC의 `~/.claude/rules/delegation.md`를 이 PC에 같은 내용으로 만들었다 (2026-11-10). 그 규칙을 따른다.
   - 난이도 3 (설계·검수·판단): Opus
   - 난이도 2 (여러 파일 구현·테스트): Codex
