## 목표
학생이 자기 지난 진단 목록을 보고, 하나를 골라 다시 본다 (F-10).
1. 목록에 자기 진단만 나온다. 진단마다 단원, 시작 날짜, 상태(진행 중, 완료, 중단)가 보인다.
2. 완료된 진단을 고르면 문제, 답안, 채점 결과, 리포트를 본다. 이 화면은 이미 있다 (`/diagnoses/[id]`).
3. 진행 중인 진단을 고르면 이어서 푼다 (F-06). 이 화면도 이미 있다.
4. 저장된 수식이 정확하게 보인다 (F-10 완료 조건).

## 이전 계획에서 이어받은 것
- 문제별 결과·리포트 화면이 이미 `/diagnoses/[id]`에 있다. F-10은 목록 화면과 진입 경로만 만들면 된다. (출처: plans/2026-11-10_grading-report.md 인계)
- 학생용 응답에는 이해도 숫자, 내부 ID, 진행 중 정답을 넣지 않는다. 응답 테스트가 있다. (출처: 같은 인계)
- `pnpm test:e2e:dev`는 백엔드를 `AI_MODE=fake`로 띄운다. 시험 계정 A·B의 진단 기록은 지우지 않고 쌓인다. (출처: 같은 인계, plans/2026-11-10_diagnosis-stage1.md 인계)
  - 그래서 목록 테스트는 기록이 아무리 쌓여도 통과하게 써야 한다. 결정 3(목록 길이)이 이 때문에 필요하다.
- 위임 (출처: 두 인계)
  - Codex·Cursor는 사용자가 연 Herdr pane에서 실행한다.
  - Codex 샌드박스는 포트·네트워크·Docker를 못 쓴다. 지시서에 "E2E 실행 금지"와 수정 허용 파일을 빠짐없이 적는다.
- 백엔드는 Secret key로 DB를 읽어 RLS를 거치지 않는다 (`docs/DESIGN.md` "인증 (F-01)"). 그래서 목록 API는 코드에서 `user_id`로 직접 걸러야 한다. 다른 사용자 기록이 섞이지 않는지 pytest와 로그인 흐름 E2E 둘 다로 확인한다 (`AGENTS.md` 3.7-5, 4.3).
- 모든 진단 API는 먼저 그 사용자의 만료된 진단을 중단으로 바꾼다 (`docs/DESIGN.md` "진단 API", 사용자 결정 2026-11-10). 목록도 같은 규칙을 따른다.
- 이 PC(회사)에서 시계가 2초 늦어 로그인 흐름 E2E가 401로 실패했다. `sntp`로 맞춘 뒤 통과했다 (2026-11-11, 아래 진행 메모).

## 결정 사항 (사용자 결정, 2026-11-11: "승인 필요한 내용 추천대로 진행하자")
아래 1~6의 **추천**을 모두 채택한다 (6은 안 A). 1단계에서 `docs/DESIGN.md`로 옮긴다.

1. **목록 데이터를 어디서 읽나**
   - 추천: 백엔드 `GET /diagnoses`. 다른 진단 화면이 모두 백엔드 API를 쓰고(`frontend/src/lib/diagnosis-api.ts`), 만료 처리도 백엔드 요청에서 일어난다.
   - 다른 안: 브라우저에서 Supabase로 직접 읽기(RLS로 자기 행만 보임). 이 경우 만료 처리가 되지 않은 상태가 보일 수 있어 추천하지 않는다.
2. **목록에 보이는 것**
   - 추천: 학년·단원 이름, 시작 날짜·시각, 상태. 상태는 `진행 중`(1단계·2단계 구분 없이), `완료`, `중단`(이유: 기간 만료 / 새로 시작)으로 보인다.
   - 완료된 진단의 단원 단계(예: "기본 이해")를 함께 보일지: 추천은 **보이지 않는다**. F-10 동작에 없고, 리포트가 아직 없는 완료 진단(AI 실패)과 섞여 상태가 복잡해진다. 근거 없음 (화면 판단).
   - 날짜는 한국 시간(`Asia/Seoul`)으로 고정해 보인다. 근거 없음 (사용자가 한국 학생이라는 서비스 전제).
3. **목록 길이와 순서**
   - 추천: 최근 시작한 순서로 20개씩, 아래에 "더 보기"를 둔다. 서버는 `limit`(최대 50)과 이어 읽기 기준(직전 마지막 진단의 시작 시각과 ID)을 받는다.
   - 이유: 시험 계정 A·B의 기록은 지우지 않고 계속 쌓인다 (`docs/DESIGN.md` "로그인 흐름 E2E"). 20개는 근거 없음.
   - 진단이 없으면 "아직 진단 기록이 없어요"와 단원 선택으로 가는 링크를 보인다.
4. **화면 위치와 진입 경로**
   - 추천: 새 화면 `/history`를 만들고, 첫 화면(단원 선택) 위쪽 로그아웃 옆에 "지난 기록" 링크를 둔다. 진단 화면(`/diagnoses/[id]`)에는 "지난 기록으로" 링크를 둔다.
   - 목록 항목을 누르면 `/diagnoses/[id]`로 간다. 진행 중이면 그 화면이 이어 풀기이고, 완료·중단이면 지금처럼 결과·리포트·중단 안내를 보인다. 화면 동작은 바꾸지 않는다.
5. **"같은 단원 동시 시작 500"을 이번에 고칠지**
   - 추천: 넣지 않는다 (`AGENTS.md` 3.4 범위 지키기). F-10과 관련이 없다. PROGRESS "나중에 볼 점"에 그대로 둔다.
6. **코드 스타일 규칙 (PROGRESS 결정 대기 항목)**
   - 배경: 진단 화면 코드가 한 줄에 여러 문장을 몰아 쓴 형태다 (`frontend/src/lib/diagnosis-api.ts:4-11`, `frontend/src/app/(protected)/page.tsx:5`). 백엔드는 이미 `ruff format`으로 포맷을 검사하지만 프론트엔드에는 포맷 검사가 없다 (`AGENTS.md` 5.2). 이번 계획도 새 화면 코드를 추가한다.
   - 안 A (추천): 이번 계획 첫 단계로 프론트엔드에 Prettier를 넣는다. `pnpm format:check`를 `AGENTS.md` 5.2 프론트엔드 검사 맨 앞에 추가하고, 기존 파일 전체를 한 번 포맷해 따로 커밋한다.
     - 근거: Prettier 문서는 포맷은 Prettier에, 버그 찾기는 린터에 맡기라고 안내한다 ([Prettier vs. Linters](https://prettier.io/docs/comparison)). ESLint 규칙과 겹치지 않게 `eslint-config-prettier`를 쓴다 ([Integrating with Linters](https://prettier.io/docs/integrating-with-linters)).
     - 대량 변경(기존 파일 전체 포맷)이라 `AGENTS.md` 3.2 확인 대상이다. 이 계획 승인을 그 확인으로 본다.
   - 안 B: 이번에는 넣지 않고 따로 작은 계획으로 한다. 새 F-10 코드는 기존 형태로 쓰이고, 나중에 함께 포맷한다.
   - 안 C: 포맷 도구 없이 "한 줄에 한 문장" 같은 규칙만 `AGENTS.md`에 적는다. 검사로 지킬 수 없어 추천하지 않는다.

   - 완료 조건: 5.2 검사 전체 통과, `pnpm format:check` 통과.
3. **목록 API** (난이도 2, Codex) — `GET /diagnoses?limit=&before=`
   - 응답: 진단 ID, 상태, 중단 이유, 시작·완료·중단 시각, 단원(학년, 이름, 출판사), 다음 쪽 기준. 이해도 숫자, 점수, 문제 내용, 내부 ID(개념·오개념)는 넣지 않는다.
   - 로그인 필수, 가입 미완료 403. 먼저 만료 처리를 한다.
   - pytest (FastAPI `TestClient`, 가짜 저장소)
     - 다른 사용자 진단이 섞이지 않는다
     - 최근 순서, `limit` 범위(1~50, 밖이면 422), 다음 쪽 이어 읽기에서 빠지거나 겹치는 진단이 없다 (같은 시작 시각 포함)
     - 만료 처리가 먼저 일어난다
     - 토큰 없음 401, 가입 미완료 403
     - 응답에 금지 항목이 없다
   - 완료 조건: 백엔드 검사 통과.
4. **목록 화면** (난이도 2, Codex) — `/history`, 첫 화면의 "지난 기록" 링크, 진단 화면의 "지난 기록으로" 링크, `diagnosis-api.ts`에 목록 함수.
   - 상태별 표시, 빈 목록 안내, "더 보기", 불러오기 실패 안내와 "다시 시도", 401·403 이동(기존 `authRedirect`).
   - 터치 대상 최소 높이 44px (`docs/DESIGN.md` "화면").
   - 단원 이름 등 서버 글은 React 텍스트로만 넣는다 (`AGENTS.md` 4.3).
   - Vitest: 상태 표시, 빈 목록, 더 보기, 실패 안내. Playwright(`e2e/`): `/history`가 로그인 화면으로 보내지는지, 360px·1280px 가로 넘침.
   - 완료 조건: 프론트 검사 통과.
5. **로그인 흐름 E2E 추가** (Opus 직접, Codex는 포트를 못 연다) — `e2e-dev/`
   - 계정 A가 방금 만든 진단이 A의 목록 맨 위에 보이고, 계정 B의 진단 ID는 A의 목록 어디에도 없다 (목록을 끝까지 읽어 확인).
   - 목록에서 완료 진단을 열면 리포트와 문제별 결과가 보이고, 문제 본문 수식이 KaTeX로 그려진다(`.katex` 있음, 렌더 오류 표시 없음).
   - 목록에서 진행 중 진단을 열면 풀이 화면이 이어진다.
   - 1280px·360px 가로 넘침 없음. 링크·버튼이 화면 안에 보인다(`toBeInViewport`).
   - 완료 조건: `pnpm test:e2e:dev` 통과.
6. **검수와 수동 확인** — 5.3 검사 루프 전체, 위임 diff 직접 검토(보안: 인증, 다른 사용자 데이터, 응답 항목, HTML 삽입).
   - 사용자 수동 확인: 데스크톱과 폰에서 목록 → 완료 진단·진행 중 진단 열기.
   - 완료 조건: 아래 완료 조건 전부.
